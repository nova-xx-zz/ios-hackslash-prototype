# 本番バックエンドの拡張・移行設計

作成・セルフレビュー：2026-10-08／版：v1.0／状態：設計案・未実装

参照基点：main `c8c9f14782ba2bad54c3b5818aca5082eed8f123`。対象は `js/cloud.js`、`js/model/save.js`、基本・詳細・本番化・課金設計書。今回の変更は設計のみ。実装済み、負荷検証済み、無停止移行可能とは判定しない。

**リリース順序（2026-10-09統合）**：Web/PWA無料公開 → Webで買い切り・消耗品の安全な台帳を構築して有料販売 → iOS展開。R1/R2は内部実装・受入順であり、初回Web有料販売前には両台帳と返金/復元が必要。将来Web購入権利をiOSで扱う際はApp Store規則を販売前に確認する。

## 1. 結論と範囲

- 最初はFirebase Authentication・Firestore・Cloud Functionsを継続採用し、WebのPSP（Stripe等）とiOSのStoreKit/RevenueCatは決済アダプターを分離する。登録者1,000人を移行条件にしない。DAU、同時API処理、バックアップ量、課金件数と実測の費用・遅延で判断する。
- 戦闘・進行・オフライン精算は端末が正。サーバーで戦闘を再計算しない。ランキング・対人・トレードを追加しない。
- サーバーは購入・権利・確定強化石のfree/paid残高・消費履歴・BOX拡張・キャラ付与を正本として持つ。クラウドセーブは進行のバックアップに限定する。
- 本番R1前に、アプリとFirebaseの接続境界、安定したアカウントID、API契約、競合制御、監視と復旧を用意する。R2前に消耗品の残高・台帳・端末反映の回復を追加する。
- 将来はAPIの実行環境、DB、認証を別々に交換できるようにする。最初からマイクロサービス、複数DBへの二重書込み、ゲーム進行のサーバー化は導入しない。
- 本書は大規模改修の範囲を減らす設計であり、移行作業が不要になる保証ではない。認証移行、データ変換、旧アプリ互換、検証は残る。

## 3. 接続境界

予定配置（ファイル・TypeScript化は本番化時に実装。現行ファイルを追加済みとは扱わない）:

| 層 | 責務 | 依存ルール |
|---|---|---|
| core/model | 戦闘・進行、DTOと純粋な計算 | Firebase、RevenueCat、HTTP、DOMを直接呼ばない |
| アプリservices | AccountService、ProgressBackupService、BillingService、AssetService | ポートのインターフェースだけを使う |
| アプリadapters | NativeSaveStore、HttpBackendClient、FirebaseAuthAdapter、RevenueCatAdapter | SDK・URL・トークン・エラーをここで変換する |
| サーバーapplication | 認証後の所有者判定、購入付与、残高消費、バックアップ保存 | repository、unitOfWork、identityVerifier、purchaseVerifierを注入する |
| サーバーadapters | Firestore・Storage・Firebase認証検証・RevenueCat通知 | 生のDocumentSnapshot、Timestamp、Callable形式を外へ漏らさない |

台帳、残高、操作結果の同時更新をrepositoryごとの独立書込みに分解しない。unitOfWork内で一意制約・条件付き更新・原子性を保つ。DB交換時は同じ契約テストを通す。UIからFirestoreへ本番課金データを直接読み書きしない。進行バックアップも本番ではAPI経由に統一し、プロトタイプの直接アクセス経路は別環境に限定する。

本番APIの入口は運営管理のHTTPSホストと`/v1`に固定する。ホスト名は公開前に確定する。Functions固有URLを画面・ゲームコードに散在させない。実行環境の変更は入口のルーティングで行う。入口の障害も監視対象とし、認証済みアカウントIDはリクエスト本文で指定させない。課金SDKによるストア購入自体はAPIの背後へ移さない。

## 4. アカウントと識別子

- `accountId`はサーバー発行UUIDv4。`billingId`は既存課金設計のUUIDv4を維持し、accountIdとの1対1対応を原子的に作る。認証の `(issuer, subject)` はaccountIdへの一意な対応表に保存する。Firebase uidを変更してもaccountId・billingId・取引IDを作り直さない。
- 新規ログインでは検証済み認証subjectだけを入力にし、並行初期化でアカウントを二重作成しない。RevenueCat App User IDはbillingIdに固定し、Apple appAccountTokenとの対応を照合する。
- 購入前に引継ぎ可能な認証へ連携する。既存匿名ユーザーは本人の認証トークンを検証して対応付ける。クライアントが申告した旧uidだけで所有者を移さない。
- 連携先が別accountIdへ登録済みなら自動統合しない。元アカウントへの復帰と個別照合を案内する。ストア取引を別accountIdへ再付与しない。
- **プロトタイプ`saves/{uid}`の進行・無料テスト購入・paid残高・購入履歴は正式版へ移行しない**。正式Web版は専用Firebaseと別オリジンで新規開始し、正式Web版の進行だけを将来iOS版の同一accountIdで復元する。
- 認証サービス全面交換は独立した工程。既存Firebaseトークンを検証できる認証ブリッジを移行期間だけ保持し、新認証の本人確認と対応付けを行う。既存セッション、Sign in with Apple等の資格情報・プロバイダー設定は別途移行検証が必要。DBをコピーするだけでは認証を移せない。

## 5. API契約と互換

| 操作例 | 契約 |
|---|---|
| `GET /v1/account` | accountId・billingId・対応API/セーブ版・利用可能機能を返す |
| `GET /v1/billing/state` | 権利・残高・拡張容量とbillingRevisionを返す。端末残高で上書きしない |
| `POST /v1/billing/reconcile` | ストア取引を再照合。通知遅延・取消・未付与から回復する |
| `POST /v1/assets/stone-consumptions` | 操作ID、期待billingRevision、装備ID、強化前値、マスター版。原子的消費と同じ結果の再取得 |
| `POST /v1/billing/campaign-grants` | サーバーの期間・受付時刻と端末踏破申告で無料権を一意記録。進行の真正性は検証しない |
| `PUT /v1/progress/backup` | backupOperationId、expectedBackupRevision、saveSchemaVersion、payloadHash、進行DTO |
| `GET /v1/progress/backup` | 検証済みの進行DTO、サーバー時刻・版・hash。復元はユーザー確認後 |
| `POST /v1/progress/backup-uploads` | 大きいセーブの段階アップロードを開始。完了APIで検証後に参照先を更新する |
| `POST /v1/webhooks/revenuecat` | iOS決済通知。提供者認証と正規の取引検証の後、耐久inboxへ保存 |
| `POST /v1/web/checkout-sessions` | ログイン済みaccountIdからサーバーの許可済商品マスターでWeb決済を開始する。クライアント申告価格を採用しない |
| `POST /v1/webhooks/payment` | Web PSPの生body署名・環境・eventId・注文accountIdを検証した後、耐久inboxに保存 |
| `GET /v1/billing/orders/{orderId}` | サーバー確定済みの注文状態を参照。成功URLへの遷移だけでは権利を付与しない |

UTCのISO日時、整数の個数、文字列のIDをDTOに使う。API版・セーブschemaVersion・課金マスター版・台帳schemaVersionは別管理。`savedAt`は参考表示に使い、競合の勝敗やキャンペーン期限を決めない。

レスポンスのエラーは `code, retryable, retryAfterMs, requestId` を持ち、UIの文言とSDK固有codeを分離する。401は再認証後に1回だけ再送、403・入力不正・版非対応は自動再送しない。競合409は同期して再確認し、黙って上書きしない。タイムアウト・429・一時的5xxは同じ操作IDで指数バックオフ＋jitter（初期1秒、上限60秒）を使う。手動再開を含めてIDを維持し、無限再送で課金を増やさない。

同じ(accountId, 操作種別, operationId)には要求hashを拘束し、違う内容なら拒否。操作記録は該当課金資産の復元・照合に必要な期間保持し、表示履歴200件や短期TTLで消さない。API入口で保持期間・旧版サポート終了を管理し、旧クライアントは更新案内と読み取り経路を残す。データを読めない旧版に書込みを許可しない。

## 6. 保存・容量・費用

### 6.1 進行DTOと競合

本番バックアップは進行だけを含める。`purchases`、`guaranteedStones`、購入由来のキャラ付与台帳・権利はAPIで同期し、端末セーブ内の値をサーバー正本として採用しない。無料キャンペーン権もサーバー記録と同期する。端末進行には課金で強化した装備やキャラ状態が含まれるが、それを購入証明としない。

保存はaccountIdごとのbackupRevisionをサーバーで増加させる。同じbackupOperationId＋hashの再送は同じ版を返す。古いexpectedBackupRevisionは409。端末ごとのdeviceIdとlocalSaveRevisionは診断用で、端末時刻の大小で競合を解消しない。競合時は端末進行を保全して候補の日時・概要を表示し、利用者が選んだ版を再保存する。自動マージしない。

端末保存の20秒間隔とイベント保存は維持する。クラウドはdirty時のみ初期300秒でまとめ、バックグラウンド送信はbest effort（OSによる完了保証なし）。手動保存と重要な変更では要求できるが、サーバーでaccountId単位のレート制限を適用する。変更hashが同じなら保存しない。オフライン中は最新バックアップ1件へ集約し、課金操作は別の永続ジャーナルに保持する。

### 6.2 容量

本番のインライン保存はUTF-8で700KiB以下を初期上限とし、Firestoreドキュメントのメタデータを含むサイズで上限を確認する。`json.length`で代用しない。大きい文字列・進行payloadの不要なインデックスは無効化する。履歴・ロット・取引を単一ドキュメントの無制限配列にしない。

700KiBを超えたら、本番R1前に実装するBlobStore経路へ送る。署名付きアップロードは所有者・サイズ・有効期限を制限し、サーバーがhash・UTF-8・schema・実容量を検証した後にbackupRevisionとblob参照を原子的に更新する。失敗時は前のバックアップを保持し、未参照blobを後から清掃する。アプリはDBの物理保存先を知らない。初期の最大進行payloadは圧縮前4MiBという予算案とし、最大BOX・所持品・図鑑の実測でR1前に確定する。超過時も端末セーブを削除せず、ローカルエクスポートと案内を用意する。

### 6.3 負荷モデル

例：1,000 DAUが1日60分プレイ。1分保存なら約60,000回/日、5分保存なら約12,000回/日。手動・離脱・課金・再送は別枠。1件100KiBを毎回送るなら後者でも約1.14GiB/日のアップロードになる。これは料金ではなく、全ユーザーがdirtyという仮定の通信量で、保存容量・ダウンロード量とは別である。

登録者数だけで費用を決めない。DAU×利用時間×バックアップ頻度×payloadサイズ、課金API回数、トランザクションの読み書き、通知・ログ・Storageを分けて予算化する。Functionsの無料呼出し回数だけで無料運営と判定しない。リージョンはR1前に主要利用者とDB/APIの近接性を検討して確定する。

## 7. 課金・非同期処理

- 取引一意キーはstore＋environment＋transactionId。WebのPSP checkout/payment IDとApp Store/RevenueCat取引IDを分離し、注文のaccountIdはサーバー側で確定する。Webhook一意キーはprovider＋environment＋eventId。operationId、billingIdと合わせて移行後も保持する。sandboxとproductionは別プロジェクト・秘密情報・台帳を使う。
- WebhookはWebの生body署名検証またはiOS通知の提供者認証・取引検証の後、受信内容・hash・状態を耐久性のあるinboxへ保存できた場合だけHTTP 200を返す。既存同一通知も200。保存できなければ5xx。受信後はworkerが処理し、失敗は再試行・隔離キュー・運営照合へ送る。クライアント成功通知だけでは付与しない。
- 重複配送・取消と購入の順不同を想定し、providerへの現在状態照合で権利を再計算する。workerはイベント1回だけの配送を前提にしない。取引台帳と付与・残高・処理状態の更新は原子的に確定する。
- ロット・消費履歴は追記型とし、修正は補償レコードで行う。履歴から残高を照合できるようにする。全ユーザーで共有する単一の残高・カウンタへ書き込まない。競合はaccountId単位で処理し、同一アカウントへの連打は制限する。
- 確定石消費は送信前に端末の永続ジャーナルへoperationId・対象・強化前値を記録する。成功後の装備反映と反映済みIDを同じローカル保存で確定する。保存失敗・再起動は同じIDの結果を再取得して回復する。復元する古いセーブへの既存操作の再適用は行わず、復元前に石が戻らない旨を表示する。
- 端末装備の強化前値は未検証の進行申告。サーバーが強化計算を行っても、その装備の真正性まで保証しない。サーバーが保証するのは台帳・残高の整合と重複消費防止。進行改ざんを許容する既存方針を維持する。

## 8. 拡張の判断と運用

初期目標（負荷試験で確定する設計値、現在の保証ではない）：通常APIのp95 1秒以内、5xx率1%未満、通知をinboxで受信してから付与までの待ち時間p95 60秒以内。ストア側・通知配送の遅延は別記する。1,000 DAUと同時1,000接続を混同しない。

| 観測 | まず行う対応 | 次に検討する変更 |
|---|---|---|
| 保存・転送量が予算超過 | dirty判定、頻度、payload、インデックスを調整 | BlobStoreへ保存先変更 |
| p95・5xx・待ち時間が継続悪化 | リトライ、競合、ホットスポット、インスタンス上限を調査 | FunctionsからCloud Run等へ処理単位で移す |
| 台帳の特定account競合 | 操作直列化・レート制限 | 必要な部分だけキュー化 |
| DB機能やコストが要件に合わない | repository契約と実測を確認 | DB移行を別工程で実施 |

requestId、operationId、イベントIDでトレースし、認証トークン・購入証明・個人情報をログへ直接出さない。API、DB、通知遅延、未付与件数、残高照合差、バックアップサイズ、月額見込みを監視する。予算50/80/100%通知、インスタンス上限、レート制限を設定する。予算通知は支出を自動停止する上限ではない。

入口で認証と所有者を検証する。Admin SDKはSecurity Rulesを迂回するため、サーバーでも所有者判定・入力上限が必須。App Checkは補助とし、認証の代用にしない。クライアントの台帳書込みを拒否するRules、IAM最小権限、Webhook秘密情報のローテーションをR1前に検証する。

## 9. 移行手順と戻し方

移行の単位はAPI実行環境→DB→認証を基本とし、一度にすべて変更しない。Functionsから別実行環境へ移す場合、DB・accountId・billingIdは維持しAPI入口を切り替える。

DB移行は次の手順に固定する:

1. schema・件数・所有者対応・取引・ロット・操作ID・revisionのエクスポート/インポート手順を作り、ステージングでリハーサルする。Firestoreエクスポートと別DB向け変換を区別する。認証データは別管理する。
2. 新DBへ初回コピーし、新DBで書込みをせず照合する。必要な差分ログをサーバーで保持する。単純な二重書込みは行わない。
3. API入口に移行状態とwriteEpochを設け、旧writerへの新規変更受付を止める。起動済み処理・worker・管理ツールをdrainし、DB側のfence/権限でも旧writerを停止できたことを確認する。クライアントフラグだけでは止めない。
4. 課金は新規購入開始を止めても、既にストアへ出た購入・遅延決済は到着する。移行対象DBと独立した耐久inboxを切替中も維持し、受信が永続化された場合だけ200を返す。処理workerは停止し、全変更経路の最終差分を同期する。
5. アカウント・取引キー・操作hash/結果・未処理通知・権利・残高・ロット・拡張回数・キャラ付与ID・backupRevisionを照合する。件数一致だけでは合格しない。不一致なら旧DBを正として再開し、切替しない。
6. 新DBを唯一のwriterにし、writeEpochを更新して入口を切り替える。旧DBは書込み不可とする。通知workerを再開し、遅延・重複通知を既存IDで処理する。旧API契約は新DBへルーティングし、旧アプリを置き去りにしない。
7. 監視・残高照合・少数アカウントの確認後に購入受付を再開する。切替中は無料プレイを続け、課金操作・クラウドは確認待ちにする。待機ジャーナルと契約を捨てない。

ロールバックは新DBの書込み開始前なら旧DBを再開できる。新DBで書込み済みなら、入口だけ旧DBへ戻してはいけない。新writerを止め、逆方向差分とinbox・operationId・revisionを同期照合してから戻す。逆変換不能なschema変更は切替前に検出し、前方修正するかバックアップから再構築して照合する。全writerの停止が確認できなければ切替を中断する。

## 10. 復旧・受入条件・実装順

進行バックアップの初期RPO目標は5分（未送信・OS終了は達成不能な場合あり）。台帳は日次バックアップ＋復元テストを用意するが、日次だけで購入を完全復旧できるとは扱わない。購入はprovider照合で回復し、消費・無料付与・拡張の操作ジャーナルは別の耐久ログまたはPITRで保護する方式をR2前に確定する。R1も権利取消・付与の回復を確認する。RTO目標4時間を初期案とし、復旧先で検証後に入口を切り替える。保持期間・アカウント削除と必要台帳保持の関係は公開前に確定する。

| ID | 受入条件（未実行） | 時期 |
|---|---|---|
| BE-01 | SDK/DBをテストアダプターへ交換してもservice・model・UIの変更不要 | R1前 |
| BE-02 | 匿名→連携・認証subject変更でaccountId/billingIdを維持。既存別accountとの自動統合なし | R1前 |
| BE-03 | 不正トークン・他account・本番へsandbox・クライアント台帳更新を拒否 | R1前 |
| BE-04 | バックアップ再送は同じ版。多端末競合・古い保存は409、端末進行を保全 | R1前 |
| BE-05 | 日本語・絵文字を含む700KiB境界、大きい進行、blob未完了・hash不一致で旧backup保持 | R1前 |
| BE-06 | 未来schemaは読み取り/更新案内、未知拡張は保持。課金残高は進行復元で巻き戻らない | R1前 |
| BE-07 | 通知保存失敗は5xx、重複・取消順不同・worker再起動で付与/取消が整合 | R1前 |
| BE-08 | 確定石消費成功直後の端末終了・保存失敗・再送で消費と反映が1回 | R2前 |
| BE-09 | 同じ操作IDの別要求を拒否。別実行環境/DBアダプターでも契約が一致 | R1/R2 |
| BE-10 | 1,000 DAU相当＋通常の10倍バーストでp95・5xx・費用・転送量を記録し目標確認 | R1前 |
| BE-11 | 遅延決済・切替中通知・旧アプリ・稼働中writerを含む移行リハーサルで台帳差0 | 移行前 |

BE-10は1,000同時利用保証ではない。実際の利用時間・API回数・最大進行payload・課金率を測定し、負荷モデルを更新する。

実装順：①accountIdと連携、DTO・API契約、環境分離 → ②QPCloudのAPIアダプターとネイティブ保存・版互換・BlobStore → ③R1の買い切り付与・inbox・復元/返金・監視/復旧 → ④R2の残高/消費ジャーナル → ⑤増加時の負荷試験・最適化 → ⑥移行が必要になった時だけ新DB実装とリハーサル。
