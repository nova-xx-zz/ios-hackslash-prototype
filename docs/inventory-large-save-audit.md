# 所持品2,500〜10,000件の性能・セーブ容量監査

更新日：2026-10-15。対象：ソードクレストの現行所持品・保存・復元・一括分解。

## 実行コマンド

- `node tools/audit-inventory-load.js`：2,500 / 5,000 / 10,000件の所持品を生成し、実際の `Save.serialize` と `Save.deserialize`、表示用分類/並び替え、手動分解、保存処理を測定する。
- `node --test tests/inventory-large-audit.test.js tests/inventory-ui-management.test.js tests/inventory.test.js`：大規模保存/復元、旧セーブの振る舞い、容量不足時の旧データ保全、疑似DOMでの80件表示、選択の安全性を確認する。
- 装備は現行の `bronze_sword`、EXP/強化石OPのExtra定義、現行N/R/SRレア度と強化値を使って生成した**人工的な大容量ストレスデータ**。実ユーザーのセーブではない。

## 調査した処理と対応

1. **一括分解の二乗時間を削減**：以前の `Inventory.disassembleItems` は、選択1件ごとに `inventory.indexOf` と `splice` を繰り返した。10,000件規模では大きな処理負荷になるため、選択参照をMapへ整理し、元の配列を1回だけ走査・同じ順序で詰め直すように変更した。ロック品、重複参照、重複選択、古い選択を確認する。
2. **所持品ソート時の繰り返し評価を削減**：能力/レア度/OP個数/分解素材量をソート比較ごとに再計算するのではなく、各アイテム一度だけ求める。画面に戻すのは元のアイテム参照で、セーブデータの順番・装備状態は変更しない。
3. **既存の80件段階表示を10,000件で確認**：所持品画面の初期表示は80行。画面外の装備データまでDOM行として作らない。絞り込み、整理候補を一括選択してもロック・強化済み・高品質OPを残すことを確認する。
4. **保存容量の圧迫を計測**：メインセーブはロスター・装備・所持品などをJSON化し、既存の単一 `jobquest_save_v1` へ書き込む。アイテム数だけでなく、OP数・装備の名称/属性などでサイズが大きく変わる。
5. **容量不足でも前のセーブを保持**：既存の `QPCore.storage.createStorage` は `setItem` の容量超過例外を捕捉し、旧データを上書きせずに保存失敗を通知する。監査では小さな残容量を模したメモリ保存先で確認する。

| 2,500件 | 516,447 | 551,451B | 5.78ms | 15.94ms | 7.70ms | 6.50ms | 3.06ms | 1,812件 | 688件 |
| 5,000件 | 1,033,191 | 1,103,195B | 6.08ms | 26.42ms | 2.09ms | 5.28ms | 2.05ms | 3,626件 | 1,374件 |

- 10,000件の初回描画は、Nodeの疑似DOMでは80行・**約14.22ms**。ブラウザのレイアウト/描画・タップ・メモリ管理を含む実機速度ではない。
- 10,000件のJSON（約2.07百万JS文字・UTF-8約2.21MB）は、仮に文字数基準5MiBの保存先ならテスト上は入る。ただしWebKit等のquotaは**文字数、UTF-16換算、他の保存キーやモード**で圧迫される可能性がある。今後数万件の保存は保証しない。
- 所持品の一括分解は元の配列参照を維持。分解された安全候補と残存貴重品の数が一致し、10,000件まで全アイテムを欠損なく保存/復元できた。
- **容量超過をわざと再現**した場合、保存操作は失敗を返し、既存のJSONは書き換えられなかった。進行後に端末を閉じれば未保存分は失われ得るので、画面の保存失敗警告を無視しないこと。

## 容量の注意点

- シミュレーションは **5MiBを仮の保存容量として比較**するが、WebKit/Safari/PWA、プライベートモード、他のキー、IndexedDBや端末の状況で保証容量は変わる。UTF-8バイト数とJS文字数は異なり得る。
- この工程では**セーブ形式の変更や、無断で装備を削除する上限は導入しない**。保存形式の圧縮、分割保存、サーバー/SQLite移行は、旧セーブ・クラウド同期・課金データ・オフライン精算の整合を含めて別工程で設計する。
- 10,000件でNodeの疑似DOMテストが成功しても、実際のiPhoneでのフレーム時間・描画性能・localStorage上限を保証しない。iPhone実機確認と、データ容量拡張方式の検討が残る。

## 結果の確認

最終的な実測値は、`node tools/audit-inventory-load.js` の `INVENTORY_LOAD` ログおよびPRのGitHub Actionsログに保存する。実行時間はCIランナー性能に依存するため、**絶対的なミリ秒をゲーム仕様の上限として固定しない**。

## セルフRV項目

- 既存の一括分解と同じ素材獲得量/残存順・ロック保護・装備参照・重複選択の挙動。
- 保存容量超過の書き込み失敗で前のJSONが残り、セーブ情報が欠損しない。
- 10,000件の保存→読込→再表示で高品質OP・ロック・強化値が欠損しない。
- UIは80行の段階表示と必要な情報のカウントを保持し、貴重品を一括で選ばない。
- 以前の関数名、参照切れ、現行の決済/自動周回/報酬ルールへの影響と正式ビルドでの読み込みを確認する。
