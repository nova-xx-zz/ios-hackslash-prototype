# ソードクレスト｜クローズドβ先行公開運用計画

- 決定日：2026-10-20
- 対象：`ios-hackslash-prototype`（検証版のみ）。正式版 `swordcrest` の本番デプロイ・課金は対象外
- 状態：**本開発を一時停止し、公開準備のみ実施。一般募集・配信は安全ゲート完了まで未開始**
- 目的：バランス・操作感・継続理由・進行不能・セーブの信頼性を少人数の実利用で確認する
- 体制：個人運用。機能追加は原則行わず、重大不具合・セーブ保全・セキュリティ・問い合わせ対応を優先する

## 1. 機能凍結のルール

1. 公開候補のmainコミットSHAを記録し、`beta/v0.1.0-candidate`等の固定リリースタグは**ゲート通過時だけ**作成する。現状は未確定
2. 開発中のダンジョン/属性/OP/ジョブ解放などの新仕様はβ期間中に通常プレイへ有効化しない。試験用URLフラグを抽選参加者へ配布しない
3. `main`へ直接コミットせず、公開準備と不具合修正は機能/修正ごとにブランチ→PR→セルフレビュー→CI→手動検証を必須とする
4. オープンPR #77（本番API基盤）は本番系の別作業として公開版へ混ぜない。#124（キャッシュテスト）もCI/差分確認後に個別判断
5. バランス変更が必要になった場合、再現条件・影響範囲・セーブ互換性・変更理由をPRに残し、ユーザーへ告知する
6. βデータ・Preview内の無料ショップ購入権利は正式版へ移行しない。βの終了日や個人情報の消去条件は募集前に公開する

## 2. X（旧Twitter）での抽選募集

- 推奨：最初に10人程度を抽選・招待し、安全確認後に累計20〜30人へ増枠。アクティブ招待は最大30人
- 応募は無料、購入・課金・景品の提供なし。対象はWebゲームを実際に遊んで所感を伝えてくれる人
- 募集ポストに**応募締切日時（JST）・当選数・抽選方法・当選連絡期限・利用条件・問い合わせ先・プライバシー案内**を明示する。未確定なら募集を開始しない
- 応募方法は「告知ポストへの返信」または専用応募フォームなど、運営が全件確認できる単一方式を採用する。任意のフォロー/リポストは集客用とし、複数回の投稿で当選確率が増えない設計
- 同一人物による多重応募を無効にすること、1人1枠、同一内容の連投を促さないことを明記
- 応募者にパスワード、Firebase UID、ゲームセーブ、住所、決済情報を送らせない。当選者のアカウント登録情報は必要最小限にする
- 抽選：応募リストを締切時に確定・重複排除→連番採番→一様乱数で順位づけ→上位から当選。入力件数、抽選日時、方法を運営ログに残す（個人情報は公開しない）
- 当選者への連絡は偽アカウント対策のため公式Xアカウントだけから行う。認証済みのGoogleアカウントを招待に使う場合、DMでパスワードや認証コードは受け取らない
- 辞退/期限切れの枠は補欠順位から繰上げ。結果連絡完了まで応募者名簿を慎重に管理し、目的外利用しない
- 無料アクセス権の抽選でもXのキャンペーン実施ガイドラインと個人情報関連法令を確認する

## 3. 公開の安全ゲート（すべて必須）

### A. アカウント/ネットワーク（未完了）
- [ ] Preview/Staging専用Firebase projectId・専用配信オリジンを明示し、本番課金/正式データから分離
- [ ] Google Auth等の再ログイン可能なアカウントと**サーバー側招待許可リスト**を実装（有効UID最大30、31人目拒否、失効・再招待・複数端末の扱い）
- [ ] トークンと許可UIDでサーバーAPIとFirestoreのアクセスを防御し、未招待・失効・別UIDへの保存/復元を拒否
- [ ] Firebase Emulatorの許可/拒否テスト、保存・復元・更新競合・レート/容量制御試験を通過
- [ ] CDN/Hosting配信方式を決定し、URL公開で静的ゲーム本体へアクセスできる場合は「30人限定」と虚偽表現しない。GitHub PagesのURL秘匿やJS内のパスワードではアクセスを制限できない
- [ ] 本番請求・有償残高付与を無効化し、Previewの無料ショップアイテムに正式購入権利がないことを確認

### B. 保存/品質（未完了）
- [ ] Preview Rules案と`js/cloud.js`送信項目の整合、デプロイ先実環境、旧保存データを検証
- [ ] CI `npm test`成功・セキュリティRV・古い関数参照/キャッシュ残りの検査
- [ ] iPhone Safari / Chrome、PC、可能ならAndroidで、初回起動/セーブ/復元/オート周回/強化/分解/クラッシュを確認
- [ ] 通信切断→復帰、端末再起動、保存サイズ上限、2ブラウザ同時更新、別端末復元の実測と事故時の復旧手順
- [ ] ソースの機能フラグが実験版機能や未販売の商品をβ利用者へ意図せず露出しないことを確認
- [ ] β前提（予告なく仕様が変わる／正式版データ非移行／無料／データ消去条件）を画面と募集要項に記載

### C. 運用/問い合わせ（未完了）
- [ ] Googleフォームを作成し、`js/contact-config.js`に**回答URL**のみ設定
- [ ] PC・iPhone Safari/Chromeからフォームを複数回送信でき、回答が運営者だけのスプレッドシートへ届く
- [ ] Firebase/Hostingの予算アラート、エラー監視、週次アクセス/費用のレビュー、緊急停止手順を確認（予算アラートは支出を自動停止しない）
- [ ] 応募情報・プレイ情報の利用目的、保存期間、問い合わせ窓口、誹謗中傷防止、ベータ利用上の注意を明記
- [ ] 公開候補コミット固定→最終テスト→ユーザーにだけ案内→初期10人で数日間安定→20〜30人へ拡大

## 4. 収集・判定方法

| 項目 | 記録内容 | 判断 |
|---|---|---|
| セーブの安全性 | 保存失敗、復元不能、データの逆行、二重付与 | **データ損失や誤付与が発生したら受付・配信を即停止** |
| 進行可能性 | 進行不能、無限周回、画面操作不可 | 致命的問題は先に修正 |
| バランス | クリア率、ジョブ偏り、難関での詰まり | まず装備/スキル/編成による複数解法を確認 |
| 継続体験 | 翌日/7日後の任意アンケート、離脱理由 | 少人数の参考値として解釈し統計的に一般化しない |
| UI | 迷った画面・面倒な操作・必要な情報 | 発生頻度と再現手順を添えて優先順位化 |
| 費用 | Firestore read/write、Hosting転送量、エラー率 | 異常増加なら新規招待停止し原因確認 |

## 5. 緊急時の運用

1. 重大不具合・認可突破・費用急増時には**新規招待を停止**し、必要に応じサーバー側招待権限/APIを失効させる
2. 影響範囲と再現条件を記録し、対象ブランチで修正・セルフレビュー・自動テスト・実機再確認
3. 同一ビルドへ無審査の直接上書きや、ユーザーデータの無断初期化をしない
4. フィードバック分類：P0＝漏えい/セーブ消失/不正付与、P1＝進行不能、P2＝操作性/頻発バグ、P3＝調整案
5. 終了時はサーバー側招待を失効し、回答フォームの受付停止、個人情報の必要期間満了後の削除、正式版非移行の再案内を行う
