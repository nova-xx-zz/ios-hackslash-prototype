# 本番化・課金方針

> 作成日: 2026-10-01。現行実装の参照基点: `f6784a0`。
> 本書は「プロトタイプ（現行のWeb版）」から「個人配信の本格iOSアプリ（将来的に課金あり）」へ進めるための方針をまとめたものである。現時点では**方針（採用予定）**であり、実装済みの内容ではない。仕様・設計を詰める際の判断基準として参照する。

## 1. 前提

| 項目 | 内容 |
|---|---|
| 開発体制 | 個人開発 |
| 配信形態 | App Store で個人として配信（将来的にAndroidも視野） |
| 収益化 | 将来的にアプリ内課金を導入する |
| 現在の段階 | 仕様・設計を詰める段階。近い将来に本格iOSアプリとして開発を進める |

## 2. 技術構成（採用予定）

| 層 | 採用予定 | 理由 |
|---|---|---|
| アプリ本体 | **Capacitor + TypeScript**（現行のHTML/CSS/JSを発展させる） | UIがテキストログ＋カード中心でWeb技術と相性が良い。1人でiOS/Androidの両方に出せる |
| サーバー | **Firebase**（Authentication／Firestore／Cloud Functions） | 個人でも運用可能で、小規模なうちは無料枠に収まりやすい |
| 課金管理 | **RevenueCat** | Appleのアプリ内課金のレシート検証・購読管理を代行する |

- サーバー処理（Cloud Functions）も JavaScript/TypeScript で書けるため、**戦闘・報酬計算のロジックをアプリとサーバーで共有できる**ことを最大の採用理由とする
- 派手な演出（スプライト・エフェクト）を重視する方針に変わった場合は、Unity等への移行を再検討する（全面書き直しになる点に注意）

## 3. データの置き場所

### 3.1 端末側の保存先（参考）

| 置き場所 | 向いているデータ |
|---|---|
| UserDefaults（Capacitorでは `@capacitor/preferences`） | 小さな設定値 |
| アプリ専用フォルダのファイル | 中規模のセーブデータ一式 |
| データベース（SQLite／Core Data／SwiftData） | 件数が多く、検索・部分更新が必要なデータ |
| Keychain | ログイントークンなどの秘密情報 |

- WebView内の `localStorage` は、端末の容量逼迫時などにOSに消される可能性があるため、**本番のセーブ置き場には使わない**
- 現行の保存処理は `saveGame()` / `loadGame()` に集約されているため、アプリ化時はこの2関数の中身を差し替える形で移行する

### 3.2 データ区分ごとの保存方針

| 区分 | データ | 置き場所 |
|---|---|---|
| 不正されると困る | 有償通貨、購入履歴、ガチャ・ドロップの抽選、オフライン進行の精算、強化の成否（課金アイテムが絡む場合） | **サーバーで計算・保存（サーバーが正本）** |
| 進行データ | ロスター、所持品、クリア状況、図鑑 | サーバーに正本、端末にキャッシュ |
| 端末だけで良い | 再生速度、表示設定、既読のお知らせ、UI状態 | 端末（UserDefaults相当） |

- **オフライン進行の経過時間はサーバー時刻で計算する**（端末の時計を進める不正の防止）
- アプリが前面に戻ったとき（起動時に限らない）にサーバーへ精算を依頼する

## 4. 設計段階でやっておくこと

1. **ゲームロジックとUIの分離**: 戦闘計算・報酬計算・オフライン精算を、DOMに依存しない純粋な関数として切り出す（現状は `js/game.js` 1ファイルに混在）。これがサーバー移行の前提になる
2. **乱数の注入**: 抽選処理で `Math.random()` を直接呼ばず、乱数生成器を引数で渡せる形にする（サーバー側抽選・検証・テストのため）
3. **経済設計の確定**: 販売するもの（有償通貨・月パス・広告削除など）、無償で手に入る量、有償／無償通貨の区別を先に決める。これがデータ構造を決める
4. **確率のデータ一元管理**: レア度の出現率などを、ゲーム内の確率表示にもそのまま使える形で1か所に定義する
5. **セーブのschemaVersion運用の継続**（現行で実施済み）

## 5. 経済設計（決定事項）

### 5.1 確定強化石（有償）

| 項目 | 内容 |
|---|---|
| 位置づけ | 装備強化を**成功率100%**で行える有償アイテム。最初の課金商品として想定する |
| 効果 | 1個消費で、通常の強化石を消費せずに必ず+1する（レア度・現在の+値を問わず1個） |
| 価値が最も高い帯 | LRなど高レア度の+99付近。強化石だけで上げると、LRの+98→+99は成功率0.5%・1回500個で、期待消費は**強化石約10万個** |
| 実装状況 | プロトタイプにUIと所持数の保存（`guaranteedStones`）のみ実装済み。機能フラグ `guaranteedStone` はOFF。入手経路（アプリ内課金）は未実装 |
| 本番での扱い | 有償通貨・課金アイテムなので、所持数と消費は**サーバーを正本**にする（§3.2） |

強化曲線（`js/data.js` の `ENHANCE_CONFIG`）:

| LRの+値 | 成功率 | 1回の消費 | 1段上げる期待消費 |
|---|---|---|---|
| +0 | 15% | 150 | 約1,000 |
| +50 | 2.5% | 329 | 約13,000 |
| +90 | 0.6% | 471 | 約78,000 |
| +98 | 0.5% | 500 | 約100,000 |

LR +0→+99 の期待消費の合計は約250万個。N/R/SR/URの曲線は従来のまま。

未決事項:
- 1個で常に+1にするか、+値が高い帯では複数個を必要にするか（現状は常に1個）
- 価格設定と、無償で入手できる経路（イベント報酬など）を設けるか
- 資金決済法（§6）との関係で、有償の確定強化石に有効期限を設けるか
- 強化石の入手ペースとの調整（現状、周回1回で得られる強化石は数十個程度のため、LRの+99は実質的に確定強化石前提のバランスになる）

### 5.2 全滅時のEXPの扱い（決定: A案）

全滅しても、それまでに勝利した戦闘のEXPは残す（通常プレイ・オフライン進行とも）。ドロップとテイムは踏破した周だけ持ち帰れる。

## 6. 課金に関するルール（日本で個人配信する場合）

> 法令・ストア規約は改正されることがあるため、課金実装前に最新情報を確認し、必要に応じて専門家に相談する。

| 項目 | 内容 |
|---|---|
| Appleのアプリ内課金 | ゲーム内のデジタル商品は原則としてAppleのアプリ内課金を利用する。手数料は通常30%、年間売上100万ドル以下なら申請により15%（Small Business Program）。日本では他の決済手段も一部認められ始めているが条件が複雑なため、当面はAppleのアプリ内課金で始める |
| 資金決済法（有償通貨） | 有償通貨は「前払式支払手段」にあたる可能性がある。基準日（3/31・9/30）時点の未使用残高が1,000万円を超えると届出と供託（残高の半分）が必要。有効期限6か月以内の場合は対象外となる例外がある |
| 景品表示法（ガチャ） | コンプガチャ（特定の組み合わせをそろえると景品がもらえる仕組み）は禁止。業界ガイドラインでは提供割合（確率）の表示が求められる |
| 特定商取引法の表記 | 有料販売を行う場合は必要。個人の住所の扱いに注意（請求時に遅滞なく開示する形で省略が認められる場合がある） |
| App Store審査要件 | プライバシーポリシー必須。アカウントを作成できるアプリはアプリ内でのアカウント削除機能が必須 |
| 未成年の課金 | 年齢別の月額上限を設けるのが業界の慣行 |
| 税務 | 売上が発生したら開業届・確定申告が必要 |

## 8. 既知の課題（2026-10-01時点、READMEとの照合結果）

現行プロトタイプでREADMEの記載と実装が食い違っていた箇所。本番化にあたって §3 の方針で解消されるものも含む。「対応」列が「済」のものは修正済み。

### 8.1 セーブ容量

| # | 重要度 | 内容 | 対応 |
|---|---|---|---|
| S1 | 高 | `saveGame()` は例外を握りつぶすため、localStorage容量（約5MB）超過時にセーブが通知なしで失敗する。所持品は上限なしで、装備1個のJSONは約150文字（約3万個で満杯） | 済（保存失敗時に画面上部へ警告。所持品の上限は未導入） |
| S2 | 高 | `markDexSeen`／`addMaterial`／自動分解設定・自動周回回数の保存が try/catch で囲まれておらず、容量超過時に例外で戦闘開始処理などが止まる | 済（全書き込みを`safeSetItem`経由に） |
| S3 | 中 | オフライン精算後の保存が失敗すると、次回起動時に同じ期間が再精算され報酬が二重付与される | 未（保存失敗時は警告のみ） |
| S4 | 低 | `enabledFeaturesAtSave` は保存されるが読まれていない（詳細設計書では「オフライン精算に利用」） | 未 |
| S5 | 低 | `itemSeq` が起動ごとに1から始まり、保存済みアイテムとIDが重複する（現状IDで検索していないため実害なし） | 未 |

### 8.2 オフライン進行

| # | 重要度 | 内容 | 対応 |
|---|---|---|---|
| O1 | 高 | オフライン計算はページ読み込み時（`loadGame()`）のみ。バックグラウンドから復帰した場合は離れていた時間ぶんの進行が失われる | 未 |
| O2 | 高 | 通常プレイではEXPが戦闘ごとに即時付与され全滅しても残るが、オフラインでは全滅した周のEXPが0になる。README／基本設計書の「EXP・レベルアップは元々踏破時のみ」もREADME自身の記述・実装と矛盾 | 済（A案: 勝利ぶんのEXPを残す） |
| O3 | 中 | 通常プレイでは生存メンバーのみEXPを得るが、オフラインでは全員が得る | 仕様として明記（個々の戦闘不能は再現しない） |
| O4 | 中 | オフラインでは道中の宝箱ドロップが計算されない（5戦のダンジョンでドロップ約1割減） | 済 |
| O5 | 中 | オフラインで戦った敵が図鑑に登録されない | 済 |
| O6 | 中 | 経過時間が短い（5秒未満、または1周の目安時間未満）と、モーダル表示なしで自動周回が停止する | 未 |
| O7 | 低 | オフラインで全滅すると完了周回数が0に戻るが、通常プレイでは戻らない | 済 |

### 8.3 モンスター合成

| # | 重要度 | 内容 | 対応 |
|---|---|---|---|
| F1 | 高 | 素材にしたモンスターの装備が所持品に戻らず消滅する（READMEに記載なし） | 済（装備は所持品へ戻す） |
| F2 | 低 | 合成に確認がない。合成後の保存は約0.4秒の遅延保存のため、その間にタブを閉じると結果が失われる可能性がある | 一部済（合成直後に即時保存。確認ダイアログは未導入） |

残りの優先度: O1（バックグラウンド復帰時の精算）→ S3 → O6 → F2の確認ダイアログ → S4・S5
