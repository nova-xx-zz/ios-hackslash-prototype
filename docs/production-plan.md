# 本番化・課金方針

> 作成日: 2026-10-01。現行実装の参照基点: `f6784a0`。
> 本書は「プロトタイプ（現行のWeb版）」から「個人配信の本格iOSアプリ（将来的に課金あり）」へ進めるための方針をまとめたものである。現時点では**方針（採用予定）**であり、実装済みの内容ではない。仕様・設計を詰める際の判断基準として参照する。

## 1. 前提

| 項目 | 内容 |
|---|---|
| 開発体制 | 個人開発 |
| 配信形態 | App Store で個人として配信（将来的にAndroidも視野） |
| 収益化 | 将来的にアプリ内課金を導入する |
| 現在の段階 | 仕様・設計を詰める段階。近い将来に本格iOSアプリとして開発を進める |

## 2. 技術構成（採用予定）

| 層 | 採用予定 | 理由 |
|---|---|---|
| アプリ本体 | **Capacitor + TypeScript**（現行のHTML/CSS/JSを発展させる） | UIがテキストログ＋カード中心でWeb技術と相性が良い。1人でiOS/Androidの両方に出せる |
| サーバー | **Firebase**（Authentication／Firestore／Cloud Functions） | 個人でも運用可能で、小規模なうちは無料枠に収まりやすい |
| 課金管理 | **RevenueCat** | Appleのアプリ内課金のレシート検証・購読管理を代行する |

- サーバー処理（Cloud Functions）も JavaScript/TypeScript で書けるため、**戦闘・報酬計算のロジックをアプリとサーバーで共有できる**ことを最大の採用理由とする
- 派手な演出（スプライト・エフェクト）を重視する方針に変わった場合は、Unity等への移行を再検討する（全面書き直しになる点に注意）

## 3. データの置き場所

### 3.1 端末側の保存先（参考）

| 置き場所 | 向いているデータ |
|---|---|
| UserDefaults（Capacitorでは `@capacitor/preferences`） | 小さな設定値 |
| アプリ専用フォルダのファイル | 中規模のセーブデータ一式 |
| データベース（SQLite／Core Data／SwiftData） | 件数が多く、検索・部分更新が必要なデータ |
| Keychain | ログイントークンなどの秘密情報 |

- WebView内の `localStorage` は、端末の容量逼迫時などにOSに消される可能性があるため、**本番のセーブ置き場には使わない**
- 現行の保存処理は `saveGame()` / `loadGame()` に集約されているため、アプリ化時はこの2関数の中身を差し替える形で移行する

### 3.2 データ区分ごとの保存方針

| 区分 | データ | 置き場所 |
|---|---|---|
| 不正されると困る | 有償通貨、購入履歴、ガチャ・ドロップの抽選、オフライン進行の精算、強化の成否（課金アイテムが絡む場合） | **サーバーで計算・保存（サーバーが正本）** |
| 進行データ | ロスター、所持品、クリア状況、図鑑 | サーバーに正本、端末にキャッシュ |
| 端末だけで良い | 再生速度、表示設定、既読のお知らせ、UI状態 | 端末（UserDefaults相当） |

- **オフライン進行の経過時間はサーバー時刻で計算する**（端末の時計を進める不正の防止）
- アプリが前面に戻ったとき（起動時に限らない）にサーバーへ精算を依頼する

## 4. 設計段階でやっておくこと

1. **ゲームロジックとUIの分離**: 戦闘計算・報酬計算・オフライン精算を、DOMに依存しない純粋な関数として切り出す。これがサーバー移行の前提になる（**完了、2026-10-05**: ルールと状態は `js/model/`、計算は `js/core/`、画面は `js/ui/`、起動処理は `js/game.js`）
   - 進め方（工程ごとにPR）: 1. ゲームの状態を1つのオブジェクトにまとめ、セーブを `js/model/save.js` へ（済み）／2. キャラまわり（作成・EXP・転職・スキルツリー）を `js/model/roster.js` へ（済み）／3. 所持品まわり（装備・自動分解・強化・合成）を `js/model/inventory.js` へ（済み）／4. ダンジョン1周の進行（道中イベント・勝利処理・テイム・オフライン精算の反映）を `js/model/run.js` へ（済み）／5. 画面の処理を `js/ui/` の画面ごとのファイルへ（`game.js` は起動処理のみ）（済み）
2. **乱数の注入**: 抽選処理で `Math.random()` を直接呼ばず、乱数生成器を引数で渡せる形にする（サーバー側抽選・検証・テストのため）
3. **経済設計の確定**: 販売するもの（有償通貨・月パス・広告削除など）、無償で手に入る量、有償／無償通貨の区別を先に決める。これがデータ構造を決める
4. **確率のデータ一元管理**: レア度の出現率などを、ゲーム内の確率表示にもそのまま使える形で1か所に定義する
5. **セーブのschemaVersion運用の継続**（現行で実施済み）

## 5. 経済設計（決定事項）

### 5.1 確定強化石（有償）

| 項目 | 内容 |
|---|---|
| 位置づけ | 装備強化を**成功率100%**で行える有償アイテム。最初の課金商品として想定する。対人戦のない1人用ゲームのため「時間を短縮する商品」と位置づけ、無課金でも時間をかければ同じ到達点に届くバランスにする |
| 効果 | 通常の強化石を消費せずに必ず+1する |
| 必要個数 | **1個＝強化石1万個ぶん**とみなし、`max(1, ceil(その段の期待消費 ÷ 10,000))` 個。N〜URの全段とLR+30付近までは1個、LR+50で2個、+70で4個、+90で8個、+98で10個。LR +0→+99の合計は約300個 |
| 無償／有償 | 所持数を無償分・有償分に分けて記録し（資金決済法の残高計算で有償分だけを数えるため）、消費は無償分から行う |
| 価値が最も高い帯 | LRなど高レア度の+99付近。強化石だけで上げると、LRの+98→+99は成功率0.5%・1回500個で、期待消費は**強化石約10万個** |
| 実装状況 | プロトタイプに必要個数の計算・強化画面のUI・無償／有償に分けた所持数の保存（`guaranteedStones: {free, paid}`）を実装済み。2026-10-07に機能フラグ `guaranteedStone` をONにし、ショップ（§5.7）で受け取れるようにした（有償分に入る）。無料配布は未実装 |
| 本番での扱い | 有償通貨・課金アイテムなので、所持数と消費は**サーバーを正本**にする（§3.2） |

強化曲線（`js/data.js` の `ENHANCE_CONFIG`）:

| LRの+値 | 成功率 | 1回の消費 | 1段上げる期待消費 |
|---|---|---|---|
| +0 | 15% | 150 | 約1,000 |
| +50 | 2.5% | 329 | 約13,000 |
| +90 | 0.6% | 471 | 約78,000 |
| +98 | 0.5% | 500 | 約100,000 |

LR +0→+99 の期待消費の合計は約250万個。N/R/SR/URの曲線は従来のまま。

### 5.2 強化の天井（実装済み、機能フラグ `enhancePity` はON）

- 今の+値で失敗に使った強化石を装備ごとに貯め（`item.pity`）、**その段の期待消費の1.5倍**に達したら次の強化は必ず成功する
- 成功または+値の変化でゲージは0に戻る。強化画面に「天井 ◯ / ◯」を表示する
- 成功率0.5%でも運の悪さに上限ができ、無課金でも到達点が見える。確定強化石は「天井を待たずに今すぐ上げる」商品として役割が分かれる

### 5.3 価格と無料配布

| 項目 | 方針 |
|---|---|
| 単価 | 1個あたり100〜160円程度を基準にする（Appleの価格帯から選ぶ） |
| まとめ買い | おまけ付きのパック（例: 10個＋1個） |
| 月パス | 毎日1個×30日など。放置ゲームと相性が良く、毎日ログインする理由にもなる |
| 通貨の形 | 当面は汎用の有償通貨（ジェム等）を作らず、確定強化石を直接販売する。直接販売でも資金決済法の対象になり得るため実装前に確認する |
| 無料配布 | 月10〜20個（LR終盤1〜2段ぶん）。ログインボーナス（7日ごとに1個など）、各ダンジョンの初回クリア報酬、達成報酬（初めてのLR入手・初めての+50など）、期間イベント |

参考: LR 1個を課金だけで仕上げると約300個（約3〜5万円）。実際には終盤の数段だけ使う想定で、主な使われ方は「LRの+90以降の短縮に約1万円」。

### 5.4 入手ペースの目標

数値の調整より先に目標期間を決め、それに合わせて「1周あたりの強化石」「確定強化石1個の換算（現在1万個）」「無料配布量」の3つを調整する。

| プレイヤー | LR 1個を+99にするまでの目標 |
|---|---|
| 無課金 | 約3〜4か月 |
| 月パスのみ | 約2か月 |
| 多く課金する人 | 数日〜即日 |

現状の目安: 1周あたり約36個（3戦のダンジョン、N・Rを自動分解）、自動周回x50を4チームで約7,000個、1日3回ログインして回すと1日約2万個。LR +0→+99（約250万個）は無課金で約4か月となり、目標とほぼ一致する。自動周回の上限（x50）やオフライン進行の上限（8時間）を本番で変える場合は見直す。

> 上の「約4か月」は旧3戦ダンジョン・天井なしの見積もりで、**2026-10-07の再計算（下記）で置き換えた**。

#### 再計算（2026-10-07、設計書レビューRV-07、`node tools/economy.js`）

前提（数値は `tools/economy.js` の `ASSUME`）:
- 周回するのは難易度の基準と同じ想定プレイヤー（初期パーティ構成＋適正装備＋素直なスキル振り）。4チームとも同じダンジョン・モードを回す
- ログインのたびに4チームとも自動周回x50を始めて放置する。1回の放置で進むのは8時間（オフラインの上限）と次のログインまでの短い方で、**全滅したチームはそこで止まる**
- N・R・SRを自動分解し、その強化石だけを数える（オプション効果「パーティの強化石」は入れない）。道中イベントは宝箱だけ入れる
- 強化するLRは持っている前提（LRを拾うまでの日数は含めない）。確定強化石は「期待消費÷必要個数」が大きい段から使う
- 無料配布は月15個、月パスは月30個、追加購入は最初に70個（1万円前後）

**1周の強化石**（踏破時）は進行帯にかかわらず約115〜120個、1周は約23秒（x1）。旧見積もりの36個から約3.3倍に増えた（5戦のダンジョン・レア敵・ボスの追加ドロップのため）。

| 周回先 | 踏破率 | 1時間あたり | 1日の強化石（1日3回ログイン） |
|---|---:|---:|---:|
| 各地方の最後のダンジョン（想定プレイヤー・推奨Lv） | 85〜91% | 約15,000〜16,000 | 約7,500〜12,800 |
| 深淵の心臓 ハード（同） | 67% | 約11,700 | 約2,700 |
| 深淵の心臓 エクストラ（同） | 38% | 約6,600 | 約750 |
| 天空宮殿（Lv100・深淵の心臓の適正装備で余裕を持って周回） | 98% | 約19,400 | 約46,000 |

**LR +0→+99の強化石**: 天井なしの期待消費は約249万個だが、天井ありでは**中央値約195万個（10%〜90%: 169万〜221万）**。確定強化石だけなら303個。

**LR 1個を+99にするまでの日数**（中央値〔10%〜90%〕）:

| プレイヤー | 余裕を持って周回・1日3回 | 余裕を持って周回・1日1回 | 想定プレイヤーで最後のダンジョン・1日3回 |
|---|---|---|---|
| 無課金 | 40日〔35〜45〕 | 102日〔91〜114〕 | 141日〔128〜156〕 |
| 月パス | 34日〔31〜38〕 | 73日〔66〜80〕 | 92日〔84〜99〕 |
| 追加購入（70個） | 29日〔25〜33〕 | 75日〔66〜84〕 | 103日〔91〜115〕 |
| 月パス＋追加購入 | 25日〔22〜28〕 | 54日〔49〜60〕 | 68日〔62〜73〕 |

**分かったこと**
1. **収入を決めるのは全滅と自動周回の上限（x50）**。1周23秒なのでx50は約20分で終わり、8時間の放置はほぼ使われない。踏破率90%前後では平均10周ほどで全滅して止まるため、想定プレイヤーの収入は余裕を持った周回の1/4〜1/5になる。ハード・エクストラは強化石の稼ぎには向かない（強化石の量は同じで、全滅しやすいため）
2. **終盤まで進めて余裕を持って周回する無課金プレイヤー（1日3回）は約40日で届き、目標の3〜4か月より大幅に早い**。目標どおりになるのは1日1回ログインの場合（約100日）
3. **月パスの効果が小さい**（40日→34日）。収入が多いぶん、確定強化石1個（強化石1万個ぶん）の価値が相対的に小さい
4. 天井によって必要な強化石は約2割減り、ばらつきも±15%程度に収まる

**目標に合わせる場合の調整案**（未決定。§5.5）
- 1周の強化石を減らす（分解で得る強化石を約0.4倍にすると、余裕を持った周回・1日3回でおよそ3か月の見込み。調整後に `node tools/economy.js` で確かめる）
- 自動周回の上限（x50）を下げる、またはログインの回数で収入が伸びにくくする（今はx50が約20分で終わるため、ログインの回数にほぼ比例して収入が増える）
- 確定強化石の換算（1個＝1万個）を上げて、月パス・購入の価値を保つ
- いずれもLR以外（SR・URの+99）や序盤の強化の手応えにも効くので、調整する時は `tools/progression.js` の進行ペースと合わせて確認する

### 5.7 ショップの商品（プロトタイプ実装済み、2026-10-07）

プロトタイプには決済が無いため、ショップ画面（設定から開く）で**購入ボタンを2回押すと無料で受け取れる**。本番化では App Store の決済の確認後に同じ処理（`js/model/shop.js` の `purchase`）で付与し、購入の記録と確定強化石の残高はサーバーを正本にする（§3.2）。価格は表示用の仮の値。

| 商品 | 形式 | 仮の価格 | 内容 |
|---|---|---:|---|
| 自動周回x100 | 買い切り | ¥480 | 自動周回の回数に x100 を追加（未購入は🔒表示。押すとショップへ）。**業火の霊峰（Lv60・20番目のダンジョン）をノーマルで踏破するまで買えない** |
| 戦闘速度x3 | 買い切り | ¥370 | 戦闘の速さに x3 を追加 |
| 戦闘速度x5 | 買い切り | ¥610 | 戦闘の速さに x5 を追加（x3を持っていなくても使える） |
| 確定強化石 1個 | 消費 | ¥160 | 有償分に1個（§5.1） |
| 確定強化石 10個＋1個 | 消費 | ¥1,600 | 有償分に11個 |
| 仲間のBOX +50 | 何回でも | ¥250 | 持てる仲間の上限を+50人（最初50人・最大1000人） |

- **仲間のBOX**: 最初の上限は50人。満員の間は「仲間を探す」ができず、テイムの抽選もしない（探索ログ・オフラインの結果で知らせる）。上限を超えて持っている仲間（以前のセーブ）は減らさない
- **戦闘速度**: 速度ボタンは持っている速さだけを x1→x2→x3→x5→x1 の順に回る。速さはオフライン精算の結果には影響しない（オフラインはx1相当の時間で計算する）
- **自動周回x100**: 序盤から買えると稼ぐ量が大きく増えてバランスが崩れるため、ゲームの後半に入る業火の霊峰（イグニス地方の最後）の踏破を購入の条件にした（`SHOP_PRODUCTS[].requiresCleared`。条件を変える時はここを書き換える）。§5.4 の再計算どおり、収入はx50でも全滅と回数の上限で決まるため、x100は「ログインの回数が少ない人の収入を増やす」商品になる。強化石の入手ペース（§5.4）を調整する時は、x100を買った場合も `tools/economy.js` で確かめる
- 購入の記録はメインセーブの `purchases`（`unlocks`・`rosterBoxes`・`history`）に保存し、クラウドバックアップにも含まれる

### 5.6 全滅時のEXPの扱い（決定: A案）

全滅しても、それまでに勝利した戦闘のEXPは残す（通常プレイ・オフライン進行とも）。ドロップとテイムは踏破した周だけ持ち帰れる。

## 6. 課金に関するルール（日本で個人配信する場合）

> 法令・ストア規約は改正されることがあるため、課金実装前に最新情報を確認し、必要に応じて専門家に相談する。

| 項目 | 内容 |
|---|---|
| Appleのアプリ内課金 | ゲーム内のデジタル商品は原則としてAppleのアプリ内課金を利用する。手数料は通常30%、年間売上100万ドル以下なら申請により15%（Small Business Program）。日本では他の決済手段も一部認められ始めているが条件が複雑なため、当面はAppleのアプリ内課金で始める |
| 資金決済法（有償通貨） | 有償通貨は「前払式支払手段」にあたる可能性がある。基準日（3/31・9/30）時点の未使用残高が1,000万円を超えると届出と供託（残高の半分）が必要。有効期限6か月以内の場合は対象外となる例外がある |
| 景品表示法（ガチャ） | コンプガチャ（特定の組み合わせをそろえると景品がもらえる仕組み）は禁止。業界ガイドラインでは提供割合（確率）の表示が求められる |
| 特定商取引法の表記 | 有料販売を行う場合は必要。個人の住所の扱いに注意（請求時に遅滞なく開示する形で省略が認められる場合がある） |
| App Store審査要件 | プライバシーポリシー必須。アカウントを作成できるアプリはアプリ内でのアカウント削除機能が必須 |
| 未成年の課金 | 年齢別の月額上限を設けるのが業界の慣行 |
| 税務 | 売上が発生したら開業届・確定申告が必要 |

### 8.6 想定プレイヤーによる難易度の基準（決定、2026-10-04）

方針: 装備とスキルを含めた「想定プレイヤー」を基準に難易度を決める（一般的なRPGの推奨戦力の考え方）。目標の踏破率は、適正装備＋素直なスキル振りで「推奨Lv: 80〜95%／推奨Lv−2: 30〜60%（ギリギリ）／推奨Lv−4: 20%未満」。

実装済み（`balance/standard-build` ブランチ）:
- `tools/lib/sim.js` に想定プレイヤーを追加。装備は部位ごとにジョブの基礎値を重みにして選び（おまかせ装備と同じ）、レア度・+値はダンジョンの `benchmarkGear`。スキルは固有ツリー→汎用①②③の順に上から振れるだけ振る（二択は左）
- `node tools/simulate.js --build` で「なし／装備のみ／スキルのみ／装備+スキル」の踏破率を比較できる
- `DUNGEONS[].power`（敵の強さの倍率、省略時1）を調整つまみとして追加（値は未設定）

- **地方**: 7地方×5ダンジョン。地方の最後のダンジョンを踏破すると次の地方の最初のダンジョンが解放される。マップは地方ごとに切り替え（`REGIONS`、`DUNGEONS[].region`）。今の5ダンジョンは1つ目の地方「ヴェルデ地方」
- **レア敵**: ダンジョンごとに2〜3体（`DUNGEONS[].rares`、テンプレートに `rare: true`）。ボス戦以外の1戦闘ごとに4%で敵1体と入れ替わる。能力値×1.3・EXP×5、倒すとSR以上の装備を必ず1個落とす（`RARE_*`、`rewards.rollRareDrops`）
- **装備のレベル**: 拾ったダンジョンの推奨Lvを装備のレベルにし、能力値は1Lvごとに基礎値の+12%（キャラの成長と同じ割合。`ITEM_LEVEL_GROWTH`）。装備の強さが一定のままだと、Lv100まで伸ばした時に終盤の装備の意味が無くなるため。想定プレイヤーの適正装備の装備のレベルは、ひとつ前のダンジョンの推奨Lv（`tools/lib/difficulty.js` の `benchmarkGearLevel`）
- **レベル曲線**: Lv15までは従来どおり（`200 + 2×Lv^3.3`）。Lv15より先は `必要EXP(15) × (Lv/15)^2.3` にゆるめ、1レベルに要る周回数が奥ほどゆっくり増えるようにする（Lv49→50 約23万、Lv99→100 約118万）。地方を追加するたびに `tools/progression.js` で到着周回を確認し、モンスターのEXPで合わせる
- 竜骨の山頂はやり込み枠をやめ、ヴェルデ地方の最後のダンジョンとして基準に合わせた（強さ倍率0.74）。装備のレベルを入れたため、洞窟1.34・遺跡1.08に調整し直した
- 進め方: 仕組み（このPR）の後、地方ごとに「5ダンジョン＋モンスター約28体（レア敵含む）」を1つのPRで追加し、毎回難易度と進行ペースを合わせる

**完了（2026-10-06）**: 7地方・35ダンジョン（推奨Lv1〜100）・モンスター200種（ボスを含む通常129種＋レア71種。最後のダンジョンだけレア敵3体）。最後のダンジョンに着くまでの累計周回は中央値で約2,100周（4パーティで並行して自動周回でき、離れている間も最大8時間ぶん進むので、遊び込む人で数週間〜数か月の見込み）。

- アビス地方では強さ倍率が0.15前後になり、0.005の差でも推奨Lvの踏破率が10〜20%動く。`--calibrate` の提案を0.005刻みにした。さらに細かい調整が要る場合は、モンスターの基礎値の側を下げて倍率を1に近づける方が扱いやすい

- 強さ倍率は奥の地方ほど小さくなる（モンスターの基礎値を地方ごとに少しずつ上げているため。実際の強さは基礎値×倍率×推奨Lvの伸び）。`--calibrate` の探す範囲の下限を0.3から0.1に広げた
- 奥の地方ほど、レベル1つの差より装備の差が大きく効く（イグニス地方では推奨Lv−4でも踏破率70〜85%）。基準の「レベルを上げても下がらない」は乱数のぶれ（±5%）と同じくらいの傾きになってきたため、強さ倍率を少し動かして収めている。地方をさらに足して判定が不安定になる場合は、比べる間隔を2レベルにするなど基準の見直しを検討する

- 進行シミュレーション（`tools/progression.js`）は、装備を「装備のレベル・レア度・強化値を合わせた能力値」で選ぶように変えた（装備のレベルを入れたため。以前はレア度→強化値の順）。到着時の装備のレベルは、どのダンジョンでもひとつ前のダンジョンの推奨Lvと一致した
- これに合わせて森の適正装備をR+1→N+1、山頂をSR+6→SR+4にし、強さ倍率を調整し直した
- サブル地方は、レベル差より装備の比重が大きい（推奨Lv−4でも踏破率70%前後）。方針Cのとおり
