# ダンジョン階層・ボス共通設計 v0.1（設計案）

> 作成: 2026-10-16 / 対象: プロトタイプ / 状態: **設計案。コード・ゲーム内データには未適用**
>
> 正本との照合: [モンスター設計](monster-design.md)、[詳細設計](detailed-design.md)、[装備・属性収集](attribute-loot-design.md)、[本番化方針](production-plan.md)、[開発優先順位](development-priorities.md)。
> 各節の「合意済み」「提案」「未決定」を区別する。既存の35ダンジョンや属性倍率、レア率をこの文書だけで変更しない。

## 1. ゲームコンセプト・変更不可の原則（合意済み）

- ダンジョンを**完全踏破した場合に限り、その周回で獲得した全アイテムを確定する**。中ボス撃破、レア/UR/LR獲得、鍵付き宝箱の解錠成功でも確定しない。
- 全滅・制限時間超過・途中撤退・攻略失敗では、その周回の**すべての未確定ドロップをロスト**。中ボスチェックポイントや有料ロスト回避は設けない。出発前から所有していたアイテム・装備は失わない。
- 戦闘勝利時に付与したEXPは既存仕様を維持し、後から全滅しても失わせない。
- プレイヤーはログから弱点や予兆を読み取り、**装備強化・天然OP厳選・継承・属性対策・ジョブ構成**を改善して再挑戦する。勝敗を操作タイミングだけに依存させない。
- 道中イベントは戦闘回数・階層進行にカウントしない。通常宝箱は自動処理、鍵付き宝箱は**盗賊系の解錠スキル習得時だけ確率判定**、不思議な泉は「周囲の魔力・霧の影響でバフ/デバフ」にする。水を自動で飲む描写はしない。
- 選択肢・YES/NO・イベント用ボタン・ログタップ・操作待ちのPAUSED状態を作らず、自動周回を停止しない。
- レア敵／中ボス／最終ボスの追加報酬であっても、**全滅時は例外なくロスト**。課金による持ち帰り保険も採用しない。

## 2. ダンジョン階層と探索構造（合意済みの配置方針）

| 形態 | 階層 | 中ボス | 最終ボス |
|---|---:|---|---|
| 初回 | 3 | なし | 3F |
| 序盤 | 5 | なし | 5F |
| 中盤 | 10 | 5F | 10F |
| 後半 | 15（上限） | 5F、10F | 15F |

- 突入時に**全階層の通常戦闘回数を一括抽選し、同一run内では固定**。ボスはその数に含めず各指定階層の末尾に別戦闘として追加。
- 通常戦闘回数の初期レンジ（設計値、調整可）：1～2F = 1～3、3～5F = 2～4、6～10F = 3～5、11～15F = 3～6。深層では最低3戦闘。
- 各通常戦闘の敵は1～5体をランダムに選出。奥へ進むほど群れ（4～5体）を増やす。**ボスを含めて戦場の敵数は常に最大5体**。
- 敵種はダンジョンごとの既存 pool/rares/boss を基礎とし、階層別の抽選重みを別定義。敵編成は戦闘開始時に確定し、再開で再抽選しない。
- 15F構成の通常戦闘は38～73回、均等抽選時の平均55.5回。中ボス2戦・最終ボス1戦がこれに加わる。長時間のリスク自体は意図したゲーム性だが、周回時間・報酬・失敗率の実測は必須。

## 3. ボスの基本定義と段階解放（**提案**）

### 3.1 必須の共通インターフェイス
- bossKind: mid / final。bossKeyは既存 ENEMY_TEMPLATES の識別子を参照し、データ未定義ならステージを生成しない。
- bossPattern: assault（攻撃型） / bulwark（防御型） / summoner（召喚型）。まずは**通常攻撃・予兆・固定条件で発動する特殊技**の共通基盤だけを実装。
- phaseRules: HP割合の閾値・一度だけの切り替え・各フェーズの行動/耐性。**序盤3Fは原則1フェーズ**、5Fは1～2、10/15Fは最大3を初期案とする。
- midBossは最終踏破条件にしない。最終ボス撃破だけがクリア条件。
- 中ボス個体の割り当ては既存35ダンジョンの敵pool・設定に沿って別表で決定。適当な新敵をここで確定しない。

### 3.2 フェーズ判定
- 参考の閾値: HP60%以下でphase2、30%以下でphase3（各ボスで上書き可）。
- HPが大きく減って閾値を2つ越えた時も、規定の移行効果を**一度だけ**処理。回復があっても前フェーズへ戻さない。死亡後に技を実行しない。
- 同じ戦闘で複数回抽選し直したり、セーブ復帰でフェーズ移行報酬を重複付与したりしない。

### 3.3 特殊行動とログ（**提案**）
| 型 | 発動条件例 | 予兆ログ | ギミックとプレイヤーの準備 |
|---|---|---|---|
| 攻撃型 | HP30%以下で攻勢 | 「敵の紋章が赤く輝いた」 | 与ダメ増・被ダメ対策。防御OPや回復役で備える |
| 防御型 | HP60%以下で鎧を強化 | 「硬い外殻が閉じていく」 | 属性・防御低下スキル・防御無視OPで対策 |
| 召喚型 | 規定のフェーズで一度召喚 | 「足元に魔法陣が広がった」 | 範囲攻撃・ジョブ編成・相手の優先処理で対策 |

- 通常敵の既存battle engineは基本通常攻撃のみ。特殊行動には**新しいBattleAction表現とオフライン共通の実行ロジックが必要**。「ログを出しただけ」で攻略上の効果が存在するように見せない。
- プレイヤーの途中タップやQTEを要求しない。予兆ログは「次回挑戦のビルド改善」に利用可能な情報とする。戦闘中の手動判断を必須にしない。
- 特殊行動には発動回数・対象・効果持続・ログIDを宣言し、同条件で連打しない。範囲攻撃・割合ダメージは実測バランスで調整。
- 召喚は**同時敵数の上限5体、召喚回数に上限、召喚された敵からのEXP/通常ドロップの無限取得禁止**。5体埋まっている場合は発動を見送るか空き枠数だけ呼ぶ。延々と召喚して300秒タイムアウトへ誘導しない。
- ボスの属性相性は**現行実装の対応属性だけ**で最初に試す。10属性・虚無・ダンジョン特効は[属性試作](attribute-loot-design.md)との統合後にfeature gateで有効化する。

### 3.3.1 ボス戦の終了条件・取り巻き対策（RV反映）
- ボス戦の勝利条件は、**ボス本体とその時点の取り巻き全員の撃破**。ボスが先に倒れても、生存中の取り巻きがいる間は勝利確定しない。召喚上限・300秒上限と一体で調整する。
- 召喚された取り巻きの撃破では**個別のEXP・装備ドロップ・テイム判定を追加しない**。特殊行動によって報酬を無制限に増やせないようにする。
- 召喚しなかった通常の取り巻きは、既存の戦闘単位の報酬設計を維持する。最終ボスの報酬抽選はボス戦勝利につき一度だけ。

### 3.4 強さの決め方
- 既存のボス一律BOSS_MULT=1.7を新階層構造へそのまま重ねない。mid/finalごとのHP・ATK・DEF・行動頻度を**独立して**調整。
- 参考初期値：中ボスHP×2.0 / ATK×1.1、最終ボスHP×3.0 / ATK×1.2（基礎の適正レベル・ダンジョンpowerを掛けた後の相対値）。正式値はシミュレーションで調整する。
- 現行の battleIndex ごとに+6%される成長補正を、全55戦超の連番にそのまま適用しない。**0～最深層で上限約+18%**など階層基準の単調な補正へ置換する試案を検証し、通常敵・ボス・モード補正の二重計算を防ぐ。
- 戦闘1回の上限300ゲーム内秒（既存基準）。HP増強による時間切れは全滅相当なので、長期ダンジョンの踏破率を測定してから上限・HPを検討する。

## 4. 戦闘ステートマシン（**提案**）

状態: PREPARED → NORMAL_BATTLE → (EVENT → NORMAL_BATTLE)* → BOSS_BATTLE → NEXT_FLOOR / CLEARED / FAILED。

- ダンジョン突入: floorPlans生成・ボス位置割当・runIdと乱数系列を生成し、戦闘回数を固定。
- 通常戦闘終了: 勝利→未確定報酬をpendingDropsへ。イベントは独立で非ブロッキング。所定通常戦闘数消化→ボスがあればボス戦、なければ次階層。
- 中ボス勝利: EXPと報酬を通常ルールで処理し、**報酬はpendingDropsのまま**。次の階層へ。チェックポイント・中間確定・途中再開解放はなし。
- 最終ボス勝利: runをCLEAREDへ遷移してpendingDropsを一度だけsettleDropsし、次ダンジョン解放。
- 敗北・撤退・timeout: runをFAILEDへ遷移し、**そのrunのpendingDropsをすべて破棄**。出撃前のinventoryは変更しない。EXPは獲得済み分を維持。
- 二重クリック・再送・バックグラウンド復帰・オフライン精算で同一runを二度settleしないよう、runId / outcome / settle済みフラグを一意に管理。課金商品の権利台帳とダンジョン報酬は別扱い。
- 状態更新は**報酬付与とrunのCLEARED確定を不可分に永続化**する。先に装備だけ追加して保存に失敗した場合や、settledだけ書いて装備付与に失敗した場合に、リロードで報酬消失／二重取りが発生しないようにする。
- 手動停止／電池切れ／クラッシュは「中ボスからの再開」を意味しない。技術的な**同一runの安全な再開**（保存済みfloorPlans・敵HP・乱数・pendingDrops等の復元）は検討するが、攻略失敗時のロストに例外を作らない。再開できないケースの扱いはユーザーへ明示し、実装前の受入条件に加える。
- 現行ではアプリ再起動時の進行中runの復元が完全ではない。新設計が「途中再開を保証する」とは**まだ言えない**。保存境界・途中中断時の失敗扱いを実装前に確定する。
- **クライアント保存だけで改ざんを完全に防げるとは主張しない**。不意の多重精算対策と、悪意あるセーブ改ざんへの対策は別の問題。将来の競争・共有機能や有料権利判定に使う結果は、サーバー側の検証・台帳で扱う。

### 4.1 データ案（互換性優先・実装未適用）
~~~ts
type BossKind = "mid" | "final";
type FloorPlan = {
  floor: number;
  normalBattles: number; completedBattles: number;
  boss?: { bossKey: string; kind: BossKind; defeated: boolean };
};
type BossBattleState = {
  bossKey: string; currentPhase: number;
  firedTriggerIds: string[]; summonsCreated: number;
  pendingActionId?: string;
};
type DungeonRunV2 = {
  schemaVersion: 2; runId: string; dungeonId: string;
  floorPlans: FloorPlan[]; currentFloor: number;
  rngState: unknown; activeBattle?: BossBattleState;
  pendingDrops: unknown[];
  outcome: "active" | "cleared" | "failed";
  settled: boolean;
};
~~~

実装時には既存の run.battleIndex・dungeon.battles・rngSource・teamBattles と接続するアダプターを設け、旧関数・旧呼び出しの残存を全検索する。v1セーブは無条件にv2扱いにせず、互換読取または明確な移行・安全な中断を設計する。

## 5. ドロップ・成長・報酬（合意と提案の分離）
- **合意済み**: 道中装備のすべては未確定、完全踏破のみ確定、失敗で全ロスト。ボス・中ボス報酬も例外なし。
- **現行**: rollBattleDropsは通常1個+確率追加、rollRareDropsはレア・ボス追加抽選。ボス固有装備は既存4%の候補がある。属性/OPの将来仕様は一部独立試作で、本体への統合は未確定。
- **提案**: 中ボスには通常戦闘の報酬に加え素材を出す余地を持たせるが、固有装備やUR/LRの保証は設けない。新しいボス固有OPは属性/装備仕様の本体統合後まで保留。
- 周回の戦闘数増加により、従来3～5戦を前提とする装備量・強化石・課金x100の価値が変化する。**一周あたり・時間あたり・踏破確率込みの持ち帰り期待値**を実測し、ドロップ率や消費量を根拠なく改変しない。
- 意図した難易度による失敗と、端末性能・クラッシュ・表示不具合でのロストを混同しないよう検証する。

## 6. 既存コードとの差分・段階的実装計画

| 現行 | 課題 | 実装段階 |
|---|---|---|
| js/data.js buildEncounter / dungeon.battles | 最終戦闘にボスを追加、最大6体になり得る | ①floorPlans/敵数上限を独立テスト |
| js/model/run.js startRun/startBattle/winBattle | 全戦闘を1次元battleIndexで管理 | ②階層・中ボス・最終ボスを統合 |
| js/core/battle.js performEnemyAction | 通常攻撃しかない | ③特殊行動・フェーズを実装 |
| js/core/rewards.js rollRareDrops/settleDrops | 旧3～5戦の報酬経済 | ④ボスを含む報酬/ロストを検証 |
| js/core/offline.js + run.js offline path | 現行とオフラインの精算経路差 | ⑤同一ロジック/決定的テスト |
| tests/difficulty.test.js / tools/simulate.js | 旧戦闘数の踏破率前提 | ⑥35ダンジョン×難易度別の再調整 |

## 7. 実装受入条件（MUST）
1. 3/5/10/15階層、通常戦闘数は突入時に全階層確定。6F以降最低3戦闘。全場面で敵は最大5体（ボス・召喚込み）。
2. 失敗・timeout・撤退・オフライン失敗のいずれでも**未確定装備0件の持ち帰り**。UR/LR・固有・宝箱・中ボス追加品に例外なし。既存所持品・装備は保持。
3. 中ボスでは次階層へ移るだけで、報酬確定もチェックポイント保存もしない。最終ボス勝利だけがsettleを呼ぶ。
4. フェーズ移行は閾値超過につき一度、召喚上限・能力倍率・300秒上限を守る。操作待ちで自動/オフラインが止まらない。
5. 通常プレイ・自動周回・オフラインで同じボスAI/戦闘ルール・報酬定義を使う（現在の既知の差分は解消かテストで可視化）。乱数シード・フェーズの再ロードによる有利な再抽選がない。
6. 属性10種・虚無・新OPは統合準備段階として、未公開機能を実戦へ紛れ込ませない。feature gateを通す。
7. 後方互換性、旧関数残存、run完了処理の冪等性と原子的保存、保存容量、4チーム同時オフライン、x100自動周回の所要時間をテスト。
8. 初期リリースのボスは最初の3Fで単純な攻撃型、5Fで防御または攻撃型を試作し、10/15Fで召喚/3フェーズを段階的に有効化する。

## 8. 実装前に残す調整項目（未決定）
- 全35ダンジョンを何階層へ分類するか、中ボスの既存敵キーをどう割り当てるか。
- フェーズ60/30%・ステータス倍率・召喚上限の実測値。
- 既存難易度の勝率目標と新たなロストリスクのバランス。ロストを救済するのではなく、攻略ログと装備対策を改善する。
- 現行の再起動/途中中断仕様からv2 runへの移行手順と、クラッシュ時の責任境界。
- 15階層周回の平均時間・装備/石の時間当たり収支。大量周回時のCPUと保存サイズ。
