# バックエンド拡張・移行設計のセルフレビュー

日付：2026-10-08／対象：[拡張・移行設計 v1.0](../backend-evolution-design.md)、要件・基本・詳細・本番化・課金設計。参照main：`c8c9f14782ba2bad54c3b5818aca5082eed8f123`。

目的：小規模から利用者が増えても、ゲーム・画面・課金を全面書き直しせず、接続部分と運用を段階的に拡張する。設計のセルフRVであり、別レビュアーによる評価・実装テスト・負荷試験・本番復旧は実施していない。

## 1. 指摘・設計への反映

P0＝本番の該当機能前に必須、P1＝増加/移行に備えて実装、P2＝運用改善。全項目「設計反映済み・実装確認待ち」であり、コードの不具合修正済みとは扱わない。

## 2. 修正後の再レビュー

- 端末進行をサーバー正本へ変更していない。購入台帳・残高と、装備の真正性・進行改ざん許容の範囲を分離した。
- identityとAPIの差替えだけでは安全な移行にならない点を確認し、トランザクションの意味・全writerの停止・最終差分・逆同期を追加した。
- 初期案の通知付与SLOはストア遅延を含むと制御不能なため、inbox受信後の時間に修正した。
- 保存頻度変更は端末保存の耐久性を下げない。クラウド5分はbest effortで、OS終了時の完了保証とは扱わない。
- 未知セーブ版の対応と、課金資産の古い進行復元を同じものにしない。装備反映済み操作は古いセーブへ勝手に再適用しない。
- BlobStoreは保存形式をAPIで隠す。ただしR1前に経路の実装・最大容量実測が必要。価格や所持上限を本書で変更していない。
- 初期に必要な境界と台帳を定義し、別DB・認証交換・移行workerの実装は必要な段階で行う。無停止全面移行を初期必須にしていない。

## 3. 検証の範囲と残る作業

実施：現行コード・既存設計との照合、外部一次資料の確認、Markdownの相対リンク・章参照・変更ファイル範囲・旧記述の整合確認。設計書の更新のみで、アプリコード・Firebase設定・本番データには変更を加えていない。

未実施：BE-01〜12、API/Rules/アダプターの契約テスト、認証連携Sandbox試験、最大BOX/所持品の容量測定、負荷試験、復元・移行・逆同期リハーサル。設計で軽減できるリスクを整理したが、販売・移行可能とは判定しない。

| 段階 | 残る必須作業 |
|---|---|
| R1前 | accountId/認証連携、API境界、進行DTO/版/容量、購入台帳/inbox、復元/返金、所有者検証、監視・権利復旧、BE-01〜07/10 |
| R2前 | 消耗品の原子処理、端末反映回復、操作ログ/PITR・保持期間、残高復旧、BE-08/09/12 |
| 利用増加時 | DAU・保存量・課金率を実測し、負荷モデル/SLO/予算を更新 |
| 実際の移行前 | 新DB契約、旧API互換、writer停止・差分照合・旧アプリと遅延決済・逆同期のBE-11/12 |

判定：設計の不足と矛盾は本PRで反映済み。段階別の実装・検証を行えば改修を接続層・保存層中心に限定しやすい。全面改修が絶対に不要という保証ではない。


## 4. PR #73との統合セルフRV（2026-10-09）

- Web先行ロードマップを正本とし、iOS先行の記述・プロトタイプ進行の移行未決は廃止した。正式版は新規開始し、正式Web版からiOSへだけ移行。
- Web用PSPチェックアウト・署名済みWebhook・注文照合APIの契約を追加。iOS決済と別アダプターで共通台帳に反映。
- R1/R2は実装順に統一し、最初の有料販売前に買い切りと消耗品の両方の安全性・返金・復元の確認を要求。
- 設計統合のみであり、Firebase本番設定・Auth連携・Web決済・サーバー台帳・負荷/移行実験は未実装。
