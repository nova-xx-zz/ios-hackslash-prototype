# クラウドバックアップ設計（プロトタイプ版）

更新日：2026-10-28。**提供状態：未提供／クラウド通信をコードで停止中**。対象：`ios-hackslash-prototype` のWeb/iPhone Safari/PWA。正式版へ移行する際は同等以上のデータ保護を維持する。

## 現在の停止方針（費用抑制）

- **コードのみ先行実装し、Firestore・Cloud Storageへの読み書きを行わない**。Firebase匿名ログインやSDKの読み込み、自動バックアップタイマー登録も行わない。
- `js/cloud.js` の `CLOUD_BACKUP_ENABLED = false` を固定値で適用し、無効時には読み書きAPIを安全に拒否する。URLクエリ、ブラウザ設定やlocalStorageによる有効化口を設けない。
- クラウドのバックアップ・履歴更新・復元ボタンは無効化し「準備中（通信停止）」と表示。保存成功や履歴があるかのように見せない。
- **端末の通常セーブ（`jobquest_save_v1`）・装備収集・探索進行・ローカルの検証用IndexedDBコピーは変更しない**。
- 新仕様の実装・単体テストは維持し、無効状態と有効状態（テスト内の疑似Firebaseに限る）の両方をテストする。
- 旧版がすでに公開されている場合、その旧版からのクラウド通信は**この未マージPRだけでは停止しない**。既存の稼働環境も止める必要があるなら、別途公開版への停止コード反映・配信確認が必要。
- **現段階ではFirebaseルール、Storageバケット、請求設定を変更・デプロイしない**。再開の際はルール検証、実機復元試験、課金監視を確認のうえ再レビューする。

## 確定仕様（提供再開後）

| 種別 | タイミング | 保持数 | 期限到達時 |
| --- | --- | --- | --- |
| 端末の通常セーブ | 既存の操作時・ダンジョン完了・定期セーブ | 従来の正本 | **変更しない**（`jobquest_save_v1`互換） |
| 自動クラウドバックアップ | 最後の**成功した自動バックアップから24時間**経過、次回起動/プレイ中 | **最大5件** | 新世代の完全保存を確認してから最古を削除 |
| 手動クラウドバックアップ | 「今すぐバックアップ」操作時。24時間制限なし | **最大5件** | 5件あれば保存を拒否、ユーザーが選択削除してから再実行 |
| クラウド復元 | 保存履歴から選択、2段階確認 | 既存の端末セーブを上書き | 既存の`prepareRestore`と安全な復元処理を再利用 |

クラウドを取得できない/認証・アップロードに失敗した場合でも**端末セーブの読み書きは継続**。バックアップ一覧に表示するのはサーバーの確定済みの履歴のみ。バックアップが完成するまで旧履歴を触らない。クラウドへの失敗分を「成功」と表示しない。

起動していない間はバックアップしない。期限超過の間も自動アップロードは起動/プレイ中に限る。Safariのバックグラウンド終了でのネットワーク送信は保証しない。Wi-Fi限定はWeb APIで判定できないため初期実装には含めない。

## 保存方式（大容量対応）

* 1文書へ全セーブJSONを送る旧`saves/{uid}`から、Firebase Cloud Storage の `swordcrest-backups/{uid}/{generation}` へ移行する。
* `CompressionStream` が使える場合はgzip圧縮、非対応なら非圧縮で保存し、いずれも元JSONのSHA-256と復元後のJSON完全一致を検証する。32MiBを安全上限とする。最大サイズは契約・料金に応じて再検討。
* Firestore `backupIndexes/{uid}` に種類、世代ID、作成時刻、元セーブ時刻、ハッシュ、圧縮種別、バイト数の**最大10件のメタデータのみ**を保存する。バックアップの本文や購入権利をFirestoreに保存しない。
* アップロード→同じオブジェクトをダウンロード→デコード・ハッシュ検証→インデックス確定→旧オブジェクトを削除、の順序。途中失敗時は旧インデックスを維持する。オブジェクト残骸については運用監視と回収処理が必要。
* 保存先はFirebase匿名認証のUID単位。Google/Appleアカウントによる引き継ぎ、複数端末競合のCAS、課金台帳は**別工程**。2端末で同一UIDを使う正式運用には、インデックスのrevision CASとサーバーAPIが必須。
* 旧`saves/{uid}`は**読み取り専用の復元フォールバック**として残し、旧履歴は削除しない。古いクライアントとの並行利用はしない。既存localStorageのキーやセーブのスキーマは変更しない。

## Firebase設定・運用上の必須作業（提供開始時に実施。現時点は実施しない）

* **クラウド機能の有効化前**に `infra/firebase/storage.preview.rules` と `infra/firebase/firestore.preview.rules` をFirebase管理画面/CLIで反映し、Firebase Storageバケットの作成・請求アラート・容量制限・認証を確認する。GitHubコミットだけではルールはデプロイされない。
* `infra/firebase/firestore.production.rules` のdeny-allは維持する。正式版のセーブは認証済みサーバーAPIと購入台帳分離を導入してから開放する。
* 手動・自動の上限5件はUI・コード双方で実施。**サーバー側に保存オブジェクト総数の絶対的な上限はない**ため、失敗したアップロードや削除失敗分は定期的に監査/清掃する。
* クライアント時刻に基づく24時間制限は改ざん可能。料金防御はFirebase/Google Cloudの予算アラート、API利用量監視、App Checkやサーバー側レート制限で補う。
* 探索中の復元は既存の自動周回停止・オフライン精算の整合を維持。報酬の二重付与と復元による抽選やり直しを含めて正式版前に別テストを設ける。

## テスト・受け入れ条件

1. 端末保存、ダンジョン周回、装備強化・分解はクラウド非接続でも利用可能。
2. 自動24時間未満で保存しない／24時間経過後の次回起動で保存／オフライン復帰後は再試行。
3. 自動5世代のローテーション、手動5件の満杯拒否、手動での削除と復元、旧セーブ読み取りフォールバック。
4. 4,143件・10,000件以上の日本語装備・OPを含むJSONがアップロード/ダウンロード後に完全一致。SHA不一致、通信断、権限不足で旧バックアップを維持。
5. iPhone Safari/PWAの実機で容量・通信断・再接続・アプリ強制終了・複数タブ・認証再取得を検証する。**実機とFirebase Emulatorでのルールテストは別途必須**。

## 費用方針

24時間あたり自動1回を目安とし、手動はユーザー操作で実施。保持するCloud Storageオブジェクトは通常最大10個（自動5、手動5）を目指す。料金は総オブジェクト容量とアップロード/検証のダウンロード帯域・リクエスト・Firestore読み書きにも依存する。**24時間設定と5件上限だけで費用が固定されるわけではない**。
