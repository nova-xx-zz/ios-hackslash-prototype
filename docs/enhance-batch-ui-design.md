# 装備一括強化 UI・処理設計

更新日：2026-10-23  
対象：プロトタイプ `ios-hackslash-prototype`  
状態：試作実装・回帰テスト対象

## 1. 背景・目的

現状の鍛冶屋の装備強化は1タップ1抽選のため、例えば+0→+14にするまで、失敗分を含め多数回のタップが必要だった。
成功率・天井・強化石の経済バランスを変えず、**「目標強化値まで、指定した消費上限内で通常強化を繰り返す」** 機能を追加する。

## 2. UI仕様

- 従来の「1回強化する」は維持する。
- 同じ強化モーダルに「目標まで一括強化」を追加する。
- 初期入力：目標 **+14**、消費上限 **500個**。入力値はそれぞれ変更可能。
- 目標の許容範囲：整数1～99（現在値以下を指定した場合は開始不可）。
- 一括強化1回の予算上限：**500個**。消費上限入力は1～500の整数のみ。
- 目標プリセット：+5 / +10 / +14 / +20。
- 押下すると「本当に目標+Nまで強化する（最大M個）」の確認状態になり、再押下で実行。確認直後の高速ダブルタップは既存の500msガードで防ぐ。
- 実行前の文言では、結果が確定しないこと・失敗時も通常石を消費することを明記。
- 結果画面には「目標達成／消費上限前停止／通常石不足」、開始値と終了値、実行回数、成功回数、失敗回数、実消費、石残数を表示。
- 目標到達後の同じ目標への再実行は不可。さらに強化したい時は新たな目標を選ぶ。
- モーダルのスクロール・iPhoneのテンキーを考慮し、2列入力と折り返し可能なプリセットを使用。

## 3. コア処理契約

`Inventory.enhanceToTarget(item, targetPlus, maxSpend)`

### 前提

- 引数は指定範囲内の整数。
- item は現在の所持品か、探索ロックされていないパーティの装備中アイテムであること。
- ユーザーの所持通常強化石が次の抽選コスト以上であること。
- クライアント側の装備強化上限は+99。

### 反復

1. 次の1抽選の必要石数を既存 `enhanceCost(item)` から算出。
2. **累積消費 + 次回コスト > maxSpend** なら抽選せず停止（端数石を消費しない）。
3. **所持通常石 < 次回コスト** なら抽選せず停止。
4. 既存の `enhanceItem(item)` を1回呼ぶ。この1回で従来と同じ確率・天井・成功／失敗処理・石消費を行う。
5. 成功時のみ+値が上がる。失敗時は同じ段で次の抽選を行う。
6. 目標に届くまで繰り返す。

### 戻り値

不正入力・対象外装備は `null`。正常な開始の戻り値は次を返す。

```ts
type EnhanceBatchResult = {
  fromPlus: number;
  targetPlus: number;
  plus: number;
  attempts: number;
  successes: number;
  failures: number;
  pityHits: number;
  spent: number; // 0～maxSpend
  reason: "target" | "budget" | "material" | "invalid";
  remainingMaterial: number;
};
```

### 保存

- 一括処理は1イベント内で同期的に行う。途中で画面を離れた場合や複数タップ時に同時処理を走らせない。
- 実際に抽選した場合のみ、終了後に `saveGame()` を呼び、一回分の一括操作をまとめて永続化する。
- 保存に失敗した場合はユーザーに警告する。従来の定期保存・保存失敗警告も活用する。
- 追加セーブフィールドは不要。強化値・天井・強化石の既存フィールドを使うので、既存セーブを移行する必要はない。

## 4. 維持する既存ルール

- N/R/SR/UR/LRの強化成功率：`js/data.js` / `js/core/enhance.js` の現行値。
- 段ごとの石コストは毎回再計算。LRのように強化段階によってコストが増える武器も超過なく止める。
- 強化失敗時は+値を下げない。天井ゲージは通常どおり加算し、成功時にリセット。
- **確定強化石（有償・無償）は一括強化の対象外。** 既存の確定強化ボタンは別操作かつ二段階確認のまま。
- 探索中・自動周回中のパーティの装備を一括強化しない。未所持アイテムを強化しない。

## 5. 主な停止例

| ケース | 結果 |
|---|---|
| N +0から+14、通常石500個以内に14回成功 | +14到達時点で停止。未使用予算は消費しない |
| LR +0から+14、成功しないまま150個を3回消費 | 450個消費、残予算50個では次の150個を払えないため停止 |
| 通常石所持5個、Nを+14まで強化 | 3個の1回目を実行し、次を払えなければ停止 |
| 目標値が現在以下、消費上限501個、未所持品 | 実行拒否・消費0 |
| 探索中に装備中 | 実行拒否・消費0 |
| +14まで到達後、再度目標+14を指定 | 開始不可 |

## 6. 実装箇所

- `js/model/inventory.js`：一括強化処理と対象装備の可否判定。
- `js/ui/models.js`：探索ロック状態をInventoryへ注入。
- `js/ui/inventory.js`：入力検証、二段階確認、結果表示、保存。
- `index.html`：入力フォーム・プリセット・ボタン・結果エリア。
- `css/style.css`：スマートフォン向けの配列と文字サイズ。
- `tests/inventory.test.js`：到達・石消費上限・天井継続・探索ロック・不正入力。
- `tests/enhance-batch-ui.test.js`：初期値・確認手順・入力・ボタンロック。

## 7. 正式Web/iOS版への移行条件

このプロトタイプの装備・通常強化石は端末のゲーム状態を更新する。正式版ではクライアントを信頼しない設計に変更する。

- サーバーが装備の所有権・探索ロック・目標・500個上限・所持石数を検証する。
- 抽選と残石・天井・+値の更新はサーバー側で原子的に確定する。
- `idempotencyKey` 等で二重送信・通信再試行による重複消費を防止する。
- 正式版では試行回数の上限／リクエスト実行時間を別途設け、一定回数を超える場合は中断・再開可能な形とする。
- 有償確定強化石を一括APIに混ぜない。購入・支払いのサーバー正本と切り離さない。

## 8. RV観点

- [ ] 消費が500を1個も超えない（例: LRの段階でコストが大きくなる）。
- [ ] 目標+14を超えて強化しない。
- [ ] 成功率・天井のアルゴリズムを重複実装していない。
- [ ] 途中の強化失敗も正しく天井に反映される。
- [ ] 確定強化石のfree/paidが不変。
- [ ] 未所持・探索ロック中の装備を拒否する。
- [ ] iPhone Safariで数字入力・2回確認・結果のスクロールを確認する。
- [ ] 既存の1回強化・確定強化・保存・強化一覧への戻り操作が動作する。
