## 1. アーキテクチャ概要

本プロジェクトはビルドツールを持たないバニラ HTML/CSS/JavaScript の単一ページアプリケーションであり、GitHub Pages 上でそのまま配信される。

```
index.html          … 全画面のDOM骨格（screenごとにsection、共通モーダル）と <script> の読み込み順
css/style.css       … 全スタイル
js/data.js          … マスターデータ（ジョブ・種族・敵・ダンジョン・装備の種類／シリーズなど）と、それを引く小さな関数
js/uniques.js       … 名のある装備（data.js の続きとして読む）
js/options.js       … 装備のオプション効果（同上）
js/core/*.js        … 画面にも状態にも依存しない計算（戦闘エンジン・報酬・強化・装備・オフライン・乱数・保存の窓口）
js/model/*.js       … ゲームの状態 S とルール（セーブ・キャラ・所持品・探索の進行・冒険の記録）
js/ui/*.js          … 画面ごとの描画と操作（タイトル・マップ・編成・詳細・探索・所持品・設定など）
js/game.js          … 起動処理（読み込み・離脱/復帰時の保存とオフライン精算・モーダルの順番）
js/cloud.js         … クラウドバックアップ（Firebase匿名認証＋Firestore）
data/*.js           … お知らせ・今後の予定（配信データ）
```

- ビルド工程がないため、すべて素の `<script>` として `index.html` の順番どおりに読み込む（順番が依存関係を兼ねる）。`js/core/`・`js/model/` は `globalThis.QPCore.*`・`QPModel.*` に公開し、Node.js からは `require` で読めるので `node --test` で単体テストする
- `js/core/` は状態を持たない計算、`js/model/` は状態 `S`（`QPModel.save.createState()`）を変更するルール、`js/ui/` は画面の描画と操作、`js/game.js` は起動とアプリの出入りだけを受け持つ。`js/ui/` の各ファイルは元の1つの game.js を画面ごとに分けたもので、トップレベルの関数・変数を共有する
- UIは `document.getElementById` によるDOM直接操作で構築・更新する。仮想DOMやフレームワークは使用せず、各画面の `render*()` 関数が対象コンテナを再構築する素朴な再描画方式を採る

### なぜこの構成か

- iPhone Safariで動くことが最優先要件であり、ビルドステップやCDN依存を持ち込むと「index.htmlを開くだけで動く」という開発中の検証容易性が損なわれる
- ゲームの正本は端末の `localStorage` に置き、Firebase は匿名認証＋Firestoreへの**バックアップ**にだけ使う（オフラインやFirebaseの不調でも遊べる）。サーバーを正本にする構成（課金・不正対策）は本番化で採用する（`docs/production-plan.md` §2〜4）
- ゲームロジックの検証が目的のプロトタイプ段階であるため、見た目はプレースホルダーでよく、DOM＋CSSで素早く反復できることを優先している

## 2. 画面構成・状態管理

### 2.1 画面（screen）一覧

`index.html` 内の `.screen` クラスを持つ `<section>` 要素が画面単位であり、`showScreen(id)` が全screenを隠してから対象のみ表示する、単純な排他表示方式でルーティングを行う（履歴・URL遷移は扱わない）。

| screen id | 内容 | 主なrender関数 |
|---|---|---|
| `screen-title` | 剣と紋章のギルド背景・2段ロゴ・Tap to Start・お知らせ・保存/復元 | `renderTitle()` |
| `screen-settings` | 設定 | 静的DOM表示（専用render関数なし） |
| `screen-announcements` | 冒険者ギルドからのお知らせ・今後の予定 | `renderAnnouncementsScreen()` |
| `screen-dex` | モンスター図鑑 | `renderDexScreen()` |
| `screen-menu` | 編成メニュー（ギルド・鍛冶屋・ショップ） | `renderPartyMenu()`（`js/ui/menu.js`） |
| `screen-farewell` | 仲間と別れる | `renderFarewell()` |
| `screen-enhance` | 装備強化（装備中・所持品の一覧） | `renderEnhanceList()` |
| `screen-shop` | ショップ | `renderShop()`（`js/ui/shop.js`） |
| `screen-jobs` | パーティ編成（ロスター一覧） | `renderJobsScreen()` |
| `screen-inventory` | 所持品一覧（未装備アイテム） | `renderInventoryScreen()` |
| `screen-create` | キャラ作成 | `renderCreateScreen()` |
| `screen-chardetail` | キャラ詳細（タブ切替） | `renderCharDetail()` |
| `screen-map` | ダンジョン選択マップ | `renderMap()` |
| `screen-battle` | ギルド背景・出発案内・探索ログ・職業紋章付きドック | `renderDock()` / `buildPartyDock()` / `renderExploreScene()` |

モーダル（`.modal-overlay`）は画面遷移とは別に `hidden` クラスの着脱で開閉する: `pickModal`（種族/ジョブ選択）、`dexModal`（図鑑詳細）、`offlineModal`（オフライン進行結果・精算の保存失敗）、`enhanceModal`（装備強化）、`announcementModal`（お知らせ）など。起動時のモーダルはキューで1つずつ開く。

タイトルは `icons/title-guild.jpg` を安全領域の外まで全面表示し、CSS Gridでロゴ／背景の剣を見せる余白／開始／下部メニューを配置する。ロゴとUIは画像に含めずHTMLで描画し、背景はpreloadする。高さ600px以下ではロゴと余白を縮め、`prefers-reduced-motion` では明滅を止める。お知らせ・セーブ・復元の処理は既存のまま利用する。

### 2.2 画面遷移の特徴

- 編成画面（`screen-jobs`）は複数の入口（タイトル／マップ／探索ドック）から開かれるため、`jobsReturnScreen` 変数に遷移元を記録し、「もどる」ボタンで適切な画面へ戻す
- 探索画面は「マップでダンジョンを選ぶ」→「出発して探索画面に戻る」という行き来を伴うため、マップ画面の「もどる」は常に探索画面（`openExploreHub()`）に戻る設計になっている
- 状態（どのタブが開いているか、どのダンジョンを選択中か等）はモジュールスコープの変数（`detailTab`, `selectedDungeonId`, `expandedTeams` 等）で保持し、画面を開き直すたびに対応する `render*()` を呼んでDOMを再構築する

## 3. データモデル概要

### 3.1 マスターデータ（`data.js`・`uniques.js`・`options.js`、不変）

- `JOBS` / `MONSTER_JOBS`: ジョブID → 基礎ステータス・アビリティ配列（テイムできる37種は型ごとの雛形から生成）
- `RACES`: 種族ID → ステータス倍率・パッシブ・経験値倍率
- `ENEMY_TEMPLATES`: 敵200種（HP/ATK/DEF/SPD/EXP・テイム可否・図鑑用属性タグ）
- `REGIONS` / `DUNGEONS`: 7地方・35ダンジョン（マップ座標・推奨Lv・戦闘数・出現プール・ボス・レア敵・解放先・強さの倍率）。`DUNGEON_MODES`（ノーマル／ハード／エクストラ）と `getModeDungeon(id, mode)`
- `RARITIES`: レア度定義（出現重み・ステータス倍率・分解時の強化石量・名前の色）
- `ENHANCE_RULES`: レア度ごとの強化成功率・費用・天井
- `ITEM_TYPES` / `ITEM_SERIES` / `ITEM_BASES`: 装備の種類26種（部位・両手持ち）×シリーズ8段階（セット効果）＝208種。`JOB_EQUIP` / `MONSTER_EQUIP`: ジョブごとに装備できる種類・二刀流
- `UNIQUE_ITEMS`（uniques.js）: 名のある装備203種（特殊効果・呪い）。`ITEM_OPTIONS`（options.js）: オプション効果

### 3.2 実行時データ（状態 `S`、可変・メインセーブに保存）

- `roster`: キャラクターオブジェクトの配列（プレイヤー作成/テイムしたキャラ全員）
- `inventory`: 未装備アイテムの配列（全チーム共有）
- `activeTeam`: 表示中のチーム番号（0〜3）
- `clearedDungeons` / `clearedHard` / `clearedExtra`: モードごとの踏破済みダンジョンIDの `Set`
- `autoRepeat[0..3]`: チームごとの自動周回の状態（稼働中か・目標回数・達成回数。保存時に挑戦中のダンジョンとモードを添える）
- `material`（強化石。メインセーブが正本）、`guaranteedStones`、`skillBooks`（予約）、`records`（冒険の記録）、`groups`（未編成グループ）、`purchases`（ショップで買ったもの）
- 端末ごとの設定（自動分解の対象、自動周回の選択回数、図鑑の発見状況、お知らせの既読、通知）は別キーに保存し、`S` に含めない

### 3.3 一時データ（永続化しない）

- `teamRuns[0..3]`: チームごとの進行中のダンジョン探索状態（ダンジョン・モード・戦闘インデックス・保留中ドロップ・石碑バフ・出撃時点の自動分解設定のスナップショット等）を並行して保持する配列
- `teamBattles[0..3]`: チームごとの進行中の1戦闘の敵配列・状態を並行して保持する配列
- キャラのHP/MP/ATB/戦闘フラグ類はロード時に毎回リセットされる（詳細設計を参照）

データモデルの詳細な構造は「詳細設計書」を参照。

## 4. 永続化方針

### 4.1 保存対象の分離

`localStorage` は用途ごとに複数のキーへ分割している（キー名は `js/core/storage.js` の `KEYS`）。

| キー | 内容 | 理由 |
|---|---|---|
| `jobquest_save_v1` | 状態 `S`（ロスター・所持品・強化石・踏破状態・自動周回・冒険の記録など）。内部に `schemaVersion` | メインのセーブデータ。報酬・強化石・自動周回の状態を同じ1回の書き込みで確定させるため、ゲームの進行はすべてここに入れる |
| `jobquest_best_cleared` | 最大クリア数 | タイトル画面表示用の軽量な値。壊れても致命的でない |
| `jobquest_material` | 強化石所持数の**互換ミラー** | schemaVersion 2 以降はメインセーブの `material` が正本。旧セーブ（schemaVersion 2 未満）の移行元としてだけ読む |
| `jobquest_autodisassemble` / `jobquest_autodisassemble_filter` | 自動分解設定 | プレイヤーの好みの設定であり、ロスターの状態とは独立 |
| `jobquest_autorepeat_target` | 自動周回の選択回数 | UIの初期選択値の記憶用 |
| `jobquest_dex_seen` | モンスター図鑑の発見状況 | 何度書いても同じ結果になる収集要素として独立管理 |
| `jobquest_read_announcements` / `jobquest_notify_auto_repeat` | お知らせの既読・通知のON/OFF | 端末ごとの設定 |

別キーにしているのは、壊れても進行に影響しない値・何度書いても同じ結果になる値だけである。各読み込みは失敗時に既定値へフォールバックする。旧版がオフライン精算の前に書いていた `jobquest_offline_settled` は使わず、起動時に消す（詳細設計§2.11）。

### 4.1a クラウドバックアップ（`js/cloud.js`）

- 起動の少し後に Firebase を読み込み、匿名ログインしたユーザーの `saves/{uid}` にメインセーブのJSONを送る。端末に保存できたたびに（`qp:saved` イベント）最短1分おきにまとめて送り、アプリを離れる時はすぐ送る
- 設定画面からクラウドのセーブで端末のセーブを置き換えて復元できる（端末より古い場合は確認する）
- 匿名ユーザーは端末（ブラウザ／ホーム画面のアプリ）ごとに別で、**別端末への引き継ぎは未対応**（Google・Appleのアカウント連携で今後追加）。確認用モード（`?debug`）ではクラウドを使わない
- クラウドは正本ではなくバックアップであり、課金・不正対策のためにサーバーを正本にする構成は本番化で採用する

### 4.2 保存タイミングの多層化

静的サイト・サーバーなしという制約上、「いつ保存が起きるか」をアプリ側で能動的に多重化する必要がある。

1. **遅延保存**（`scheduleSave()`, 400msデバウンス）: キャラ詳細・編成画面を開くたびに呼び出し、操作の合間に保存する
2. **チェックポイント保存**（`finishRun()` 内で明示呼び出し）: ダンジョンクリア／全滅という重要な区切りで確実に保存する
3. **離脱時保存**（`visibilitychange` でタブが非表示になった時、`pagehide`）: iOS Safariでは `beforeunload` が確実に発火しないため `visibilitychange` を主軸に据えている
4. **定期保存**（`setInterval(saveGame, 20000)`、画面が見えている間だけ）: 上記のいずれも取りこぼした場合の最終防衛ライン
5. **精算後の保存**: オフライン精算の報酬と自動周回の停止を1回の保存で確定する（失敗時は定期保存で再試行し、保存されないまま終了したら次回起動時に精算し直す）

### 4.3 ロード時の整合性処理

`loadGame()` はセーブデータのロスターに対し、HP/MP/ATB/生存フラグ/防御フラグを毎回再計算・リセットする。これは「戦闘中にタブを閉じた」場合でもセーブデータが壊れた状態（例: HP0で保存されたキャラがロード後も戦闘不能のまま）にならないようにするための設計判断である。

## 5. 主要システムの設計方針

### 5.1 種族×ジョブによるステータス設計

キャラの実ステータスは「（ジョブの基礎値 × レベル成長率 × 種族倍率 ＋ 装備の能力値 ＋ スキルツリーの加算 ＋ オプション効果の固定値）×（1＋セット効果・名のある装備・オプションの割合）×（ダンジョン内バフ）」という積み上げ式で算出する（`computeStats()`。順番の詳細は詳細設計§2.1）。ジョブが「役割・技構成・装備できる種類」を、種族が「ステータスの傾向・パッシブ1つ」を担当する、という責務分離により、8種族×12ジョブ（＋モンスター37種）の組み合わせを1つの計算関数で表現できるようにしている。

### 5.2 転職とジョブ別レベル管理

キャラは `jobLevels`（ジョブID→レベル/EXP）を個別に保持し、転職時は現在のジョブの進行を書き戻してから切り替え先の記録を復元する。これにより「メインジョブを変えてもこれまでの育成が無駄にならない」という要件を、レベルという単一の数値ではなくジョブごとの辞書で表現している。

### 5.3 速度依存ATB戦闘エンジン

`requestAnimationFrame` ループ（`loop()`/`tick()`）が経過時間 `dt` ごとに全キャラ・全敵のATBゲージを `SPD × ATB_RATE × dt` で加算し、100に達した順に行動させる。コマンド入力を挟まず、行動可能になった瞬間に `chooseAction()`（AI）が自動で技を選び即実行する。これにより「操作不要のフルオート」と「SPDが高いほど行動回数が増える」というハクスラ的な手数のジャンケンを両立させている。

### 5.4 ドロップ確定のタイミング設計（保留ドロップパターン）

戦闘中・道中イベントで得たアイテムは即座にインベントリへ入れず、`run.pendingDrops` に一旦積んでおき、ダンジョンを**踏破した場合のみ** `settlePendingDrops(run)` で確定させる。全滅時はこの配列を単に破棄する。テイム判定と同じく「踏破時のみ確定」に揃えている。一方EXP・レベルアップは戦闘に勝つたびに即時反映し、全滅しても勝利ぶんは残す（放置ゲームとしてのストレスを抑えるため。オフライン進行も同じ扱い）。

なお `settlePendingDrops` は自動分解の設定を、出撃時（`startDungeon`）にその周回の `run` へスナップショットした値（`run.autoDisassemble` / `run.autoDisassembleRarities`）で参照する。ライブのグローバル設定を直接見ないことで、複数チームが同時に探索していても「途中で設定を変えたら、今まさに探索中の別チームの周回結果まで変わってしまう」という事故を防いでいる。この設計のおかげで、自動分解の設定画面自体はどのチームが探索中でもロックする必要がない。

### 5.5 レア度・強化の確率設計

レア度抽選は重み付き抽選（`rollRarity()`）で行い、上位レア度ほど出現重みを指数的に小さくすることで「URは10周に1回出れば運がいい、LRは100周に1個」という体感を作っている。強化成功率も同様に、+が上がるほど指数的に減衰する（下限3%）ことで、上位レア度装備ほど周回による強化石の蓄積が長期的な目標になるよう設計している。具体的な数式は詳細設計書を参照。

### 5.6 テイム・モンスター合成

テイムは種族専用ジョブ（`MONSTER_JOBS`）を持つ37種（各地方5〜6種）に限定し、専用ジョブが未整備な敵は図鑑・ドロップ要素としてのみ機能させることで、データ追加（敵の種類を増やす）と機能追加（テイム対象を増やす）を分離している。テイムしたモンスターはどこで仲間にしてもLv1から始まる。モンスター合成はテイムモンスターの重複個体の使い道として、「種族の基本EXP（その種族が出る一番早いダンジョンのLvで1レベル分）＋積み上げたEXPの半分」（同族は1.5倍）を還元し、ロスター整理と育成短縮を両立させる。お気に入りのモンスターは素材にしない。

### 5.7 自動周回とオフライン進行

自動周回は「クリアごとに同じダンジョンへ再出撃」を繰り返す単純なループ（`finishRun()` 内の分岐）で実現する。チームごとに独立した状態（`autoRepeat[i]`）として管理するため、複数チームが同時に自動周回を回すことができる。静的サイトはバックグラウンドで処理を継続できないため、「本当にバックグラウンド実行する」のではなく、**離脱時刻と復帰時刻の差分から結果を事後的にシミュレーションする**アプローチ（`runOfflineProgress()`）を採用した。各周回は通常プレイと同じ戦闘エンジン（`QPCore.battle.simulate`）でキャラの写しを実際に戦わせて勝敗と所要時間を決め、既存の報酬計算式（EXP付与・ドロップ抽選・自動分解・テイム抽選）を流用して結果を一括反映する（以前のパーティ平均Lvから踏破確率を概算する方式は、戦闘シミュレーションより大幅に楽観的だったため廃止した）。ただし石碑の加護の省略など通常プレイとの差があり、完全に同じ結果は保証しない（差は詳細設計§2.11の表）。精算した報酬と自動周回の停止は1回の保存で確定する。オフライン計算もチームごとに独立して行うため（`runOfflineProgressForTeam()`）、離れていた間に複数チームが同時に自動周回していれば、それぞれの結果が個別に算出され「おかえりなさい」モーダルにまとめて表示される。

### 5.8 並行探索の実現方式とロック粒度

I〜IVの4チームを同時に探索させるにあたり、既存の「画面に表示している1チーム分の状態」という前提を「4チーム分の状態を配列で保持し、表示中のチームだけDOMへ反映する」という形に変えた。具体的には、メインの `requestAnimationFrame` ループ（`tick()`）は毎フレーム4チーム全ての ATB を進め（`tickTeam()`）、DOM更新（`updateBattleDOM()` やログのDOM追加）だけを「現在表示中のチーム（`activeTeam`）」に限定する。ログはテキスト量が多く再生成コストも無視できないため、チームごとの履歴を軽量なデータ配列（`teamLogs[i]`）として保持し、表示中チームの分だけDOMに反映・タブ切替時に一括再構築する（表示していないチームのログはデータとして積み上がるだけでDOM操作は発生しない）。

複数チームが同時に状態を持てるようになったことで、「ダンジョン出撃中は編成・装備・スキル・転職・合成の変更を一切禁止する」という旧来のロック（画面そのものを丸ごと無効化）は、全チームを巻き込む過剰な制約になってしまう。そのため、ロックの単位を「アプリ全体」から「探索中の個々のチーム」に変更した。キャラ詳細画面は、そのキャラが探索中チームに所属する場合のみ `pointer-events: none` で読み取り専用にし（`renderCharDetail()` 内の `locked` 判定）、パーティ編成画面のドラッグ&ドロップも移動元・移動先いずれかのチームが探索中なら開始・受け入れの両方をブロックする。自動分解の設定だけは前述の出撃時スナップショット方式によりロック自体が不要になった。

## 6. UI設計方針

- 探索画面は `icons/explore-guild.jpg` を全面背景にし、青緑・古金色のテーマを `#screen-battle` に限定して適用する。未出発でログがないときだけ出発案内を表示し、未編成なら編成への導線に切り替える。背景は共通のギルドの入口を表すもので、ダンジョン固有の景観ではない。HP・MP・レア度の意味色と既存の戦闘処理は保持する
- 待機案内 `exploreWelcome` と `logFeed` を別DOMにし、最初のログ追記で案内を隠す。帰還後もログを保持し、パーティ切替で該当チームの履歴と案内を再構築する。案内ボタンは既存のマップ／編成ボタンに接続し、探索ロック中には遷移しない。ログカードは不透明度95%の暗色を用い、背景上でも本文を読めるようにする
- 下部ドックは従来どおり実測した `--dock-offset` とセーフエリアを使用する。案内領域は短い画面でスクロール可能、高さ650px以下では職業紋章を省く。背景には常時アニメーションや毎フレームの画像処理を加えない
- 戦闘・敵の表現はグラフィックを持たず、テキストログ（イベントごとに色分けされたカード）と残り状況のテキスト表示（`enemyRoster()`）で完結させる。これはプロトタイプ段階でシステムの面白さを検証することを優先し、アセット制作コストをかけない判断による
- パーティ編成のメンバー移動は、iOS SafariがHTML5 Drag & Dropに非対応であるため、Pointer Eventsベースの独自実装（長押し判定＋ゴースト要素追従）で行う
- モーダル（種族/ジョブ選択・図鑑詳細・強化・オフライン結果）は共通の `.modal-overlay` / `.modal-card` パターンを使い回し、背景タップでの閉じる挙動も共通化する

### 7.1 ジョブとツリーの責務（固有ツリー＋汎用3枠の交換まで実装済み。ブック経済・ブック適性・極みは未実装）
- 種族は基礎傾向、ジョブは固有技・専門性、ツリーは追加技能・戦い方、分岐は特化方向を担当する
- **実装済み**: 1キャラは「固有ツリー（系統タグごとに1本、交換不可）」＋「汎用ツリー3枠（枠ごとに2択から交換可能）」の計4本を同時に持つ。SPは4本で共有する1つのプールから消費する
- 固有ツリーはジョブ系統タグ（下表）ごとに固定1本。汎用ツリーは全ジョブ共通のプールから、`GENERAL_SLOTS`が定義する3つの固定枠（枠ごとに交換候補2種）で構成する。交換すると、その枠に振ったSPだけリセットされ、固有ツリー・他の枠には影響しない
- **未実装のまま据え置き**: 汎用ツリーの交換をスキルブックの入手（ドロップ）・鑑定所・所持品消費と結びつけるブック経済。現状の交換は無償・即時（探索中チームのみロック）で、ブック経済実装後はこの簡易交換を置き換える
- 基本職は同じ系統内で使用可能な書の範囲を広く取り、上級職には専門性に応じた適性制限を加える。タグだけでは全職の範囲が同じになるため、ツリーごとに対応ジョブを絞る（**未実装**。固有ツリーは基本職／上級職とも同じ系統タグのツリーを共有し、汎用ツリーは全ジョブで同一のプール・候補を共有する）
- 極みは対象基本職Lv99以上で解放し、別ジョブIDを作らず、既存基本職の進行レコードに状態を追加する。同じジョブと同じツリーでも、極みの適性補正によって異なる完成形を作る（**未実装**）

| 系統タグ（新設） | 現行基本職 | 現行の派生上級職 |
| --- | --- | --- |
| warrior | warrior（せんし） | swordmaster（けんごう） |
| magic | mage（まほうつかい） | archmage（だいまどうし） |
| healer | priest（そうりょ） | archpriest（だいしんかん） |
| rogue | thief（とうぞく） | ninja（にんじゃ） |
| martial | monk（ぶとうか） | saintfist（けんせい） |
| dark | darkknight（あんこくし） | reaper（しにがみ） |

この表は既存の転職経路を維持する。会話の例にあった「せんし→けんごう→けんせい」という新しい転職経路は採用しない。複合タグ・ツリー名・個別適性は後からマスターに追加できる構造とする。

実装済みの固有ツリーは `JOB_TAGS`／`EXCLUSIVE_TREES`（`js/data.js`）として上表のとおり定義した。汎用ツリーは`GENERAL_TREES`（6種の全ジョブ共通アーキタイプ: 攻め/俊敏/守り/吸魂/支援/魔導）と、それを3つの固定枠に割り当てる`GENERAL_SLOTS`（枠ごとに交換候補2種を固定）で定義する。進行（習得済みノードのランク）は `c.jobLevels[jobId].skillTree` にキャラ・ジョブごとに保持し、固有ツリーは`exclusiveRanks`、汎用3枠は`general.slot1〜3.{treeId, ranks}`に分けて記録する。同じ系統タグの基本職／上級職間でも転職すればそれぞれ別に育成する（ツリーの内容は共有するが進行は共有しない）。

### 7.2 マスターと処理の分離（未実装。Stage1/1.5は簡易配置で実装）
Stage1〜1.5（固有＋汎用3枠の標準ツリー）はこの節の想定より小規模なため、専用ファイルへの分離を行わず `js/data.js`（マスター: `JOB_TAGS`/`EXCLUSIVE_TREES`/`GENERAL_TREES`/`GENERAL_SLOTS`）と `js/model/roster.js`（処理: ツリー取得・SP計算・ノード習得・枠交換・パッシブ集計）・`js/ui/detail-tree.js`（分岐図UI描画）に追加した。スキルブック・鑑定所・極みなど後続の大きな機能を追加する段階になったら、以下の分離方針へ切り替える。
将来追加する定義は大きな `data.js`／`game.js` に集中させず、責務別に管理する。

| 設計上の配置 | 役割 |
| --- | --- |
| `data/skill-trees.json` | ノード、前提、分岐、効果、適性 |
| `data/skill-books.json` | 本とツリーの対応、レア度、鑑定費用、ドロップ設定 |
| `data/job-mastery.json` | 基本職の極み条件と効果 |
| `data/announcements.json` | 公開対象のお知らせの本文・改訂・再表示指定 |
| `data/roadmap.json` | プレイヤー向け予定・現在の情報公開段階 |
| `js/announcements.js` | 既読管理、一覧・詳細、起動時表示キュー |
| `js/skill-system.js` | ノード操作、適性判定、ツリー効果計算、ブック操作 |

静的JSONを同一オリジンで取得する。ビルドツール・フレームワーク・サーバーは追加しない。取得後に型・ID・参照先を検証し、不正な告知はスキップ、不正なプレイ用マスターは該当操作を無効化する。ファイル直開きの検証環境でfetch制約がある場合は同じ定義のJS配布形式を選べるが、データとロジックの分離は維持する。

告知・ロードマップはゲーム開始の必須依存にしない。公開済みのスキル機能は有効なマスターを読み込んでからセーブ復元・オフライン計算・ステータス計算を行う。画面表示を急ぐためにツリー未読込の状態で報酬計算しない。未読込時もツリー進行の保存値は保持する。

### 7.3 ブックのライフサイクル（未実装）
1. 通常／オフライン探索の共通ドロップ処理で抽選し、踏破時に共有ブック所持品へ確定する
2. 未鑑定の本ではレア度と費用だけを表示する
3. 鑑定操作は共有の強化石を消費し、同じ個体を鑑定済みに更新する。キャラには適用しない
4. 使用対象・適性・探索ロック・機能公開状態を確認して、変更内容と1冊消費を確認画面へ表示する
5. 確定時に対象ジョブのツリーを交換し、1冊だけ消費して保存する。戻す場合も対応する本を必要とする

装備 `inventory` の「必ずslot/stat/valueを持つ」という前提を壊さないよう、セーブ内では `skillBooks` を独立配列とする。UIでは共有所持品の「装備／スキルブック」切替で統合する。鑑定所はそのブック一覧から開く。鑑定は対象キャラを変更しないため探索中も利用可能、ブック使用・SP操作・極み解放は対象チームのロックに従う。

装備強化と鑑定は同じ `material` を使用する。鑑定前の残高検証・連打防止・保存失敗時の復元を行い、費用だけ消えて本が変化しない状態を防ぐ。確定済みの鑑定を再読込で再抽選しない。鑑定が強化石の主な用途を過度に圧迫しないよう費用・入手量を調整する。

### 7.4 戦闘との統合（固有＋汎用3枠の範囲は実装済み。条件付き効果・極みの寄与は未実装）
- 取得ノードから常時パッシブ・アクティブ技を解決する。`treePassiveTotals(c)`/`treePassive(c,key)` が固有ツリー＋汎用3枠ぶんを合算したうえで、種族の `racePassive()` と同じキー（`critBonus`/`lifesteal`/`healBonus`/`dmgTakenMult`/`mpCostMult`）へ加算・乗算し、既存の種族分と合算して適用する（`computeStats`/`mpCostFor`/`performCharacterAction`/`performEnemyAction`）。装備・極みの寄与を区別する設計は据え置くが、種族とツリーの二重適用は起きない
- ツリーで取得したアクティブ技は通常のアビリティと同じ形のオブジェクトとして `availableAbilities()` に追加し、既存AIの優先度・ターゲット選択へそのまま乗る。未取得のノードは候補に入らない
- 条件付き効果（HP変化や行動時などに限定したトリガー）、反撃・状態異常のような新たな戦闘ルールは**未実装**のまま。標準ツリーのノードは常時パッシブとアクティブ技のみで構成し、これらの機構を待たずに公開できる範囲に絞った
- 同一効果の加算／乗算は種族と同じキー単位で区別し、加算系(`statAdd`/`passiveAdd`)は合計へ加算、乗算系(`passiveMult`)は乗算で重ねる。上限・排他はノードの `exclusiveGroup`（同グループ内は同時習得不可）で表現する
- オフライン進行は現行でも実戦の完全再現ではない。標準ツリー公開時点での踏破確率・新ビルドの差分検証は今回のStage1では行っていない（調整値は初期実装のための仮値であり最終バランスではない）

### 7.6 保存互換と機能の公開制御（実装済み）
- 既存の `jobquest_save_v1` を読めるまま拡張し、内部 `schemaVersion` と追加フィールドを持たせる。欠落しているフィールドだけ既定値を補い、レベル・EXP・装備・所持品を初期化しない
- ジョブ別レコードへ `skillTree` と `mastery` を追加する。レベル書き戻し（`gainExp()`/`newCharacter()`/`switchJob()`）はオブジェクトを丸ごと代入せず、既存レコードへマージする処理に改修済み（`skillTree`を含む追加フィールドを転職・レベルアップで失わない）
- 新規本・SP・極みは未公開状態ではドロップしない／取得できない／効果を適用しない。セーブに存在する値は消去せず保持する
- スキルツリー／スキルブック／鑑定所／極みの機能ゲートを持つ。極みはツリーとブック・鑑定の公開を前提にする
- 公開判断は配布バージョンの明示設定による。日付は告知の表示制御用とし、ゲーム機能の自動解放条件にしない

## 8. 本番課金の構成案（未実装、2026-10-08）

[課金設計書](monetization-design.md) §7〜9を正本として本番を設計する。現行プロトタイプのFirebaseバックアップへ購入データを保存するだけでは本番課金基盤としない。

- **識別と復元**：ゲームアカウントとサーバー発行billingIdを1対1で管理。購入前に引継ぎ可能アカウントへ連携する。RevenueCatの復元設定は元App User IDを維持する案とし、設定とtokenの対応をSandboxで確認する。
- **資産の正本**：購入台帳・買い切りの権利・有償の確定強化石・BOX拡張・キャラ付与はサーバー正本。RevenueCatの権利表示だけを消耗品残高としない。
- **戦闘の実行**：固定刻みは0.05秒（2026-10-08決定）。速度は固定刻みの実行回数を変え、戦闘に渡すdtは変えない。画面の戦闘・オフライン精算・シミュレーターで同じ実行方式を使い、チーム別乱数と行動順を固定する。
- **進行の扱い**：ランキング・対人・トレードは設けない（2026-10-08決定）。進行（Lv・装備・所持品・通常の強化石・踏破・オフライン精算）は端末のセーブを正とし、サーバーはバックアップだけを持つ。戦闘の再計算・実行lease・区間管理は行わない。
- **購入の履行**：検証済み取引IDを一意化し、契約時のマスター版に従って付与する。販売停止は新規決済を止めるだけで、支払済み未付与の契約を消さない。
- **移行**：無料テスト・Sandbox・Productionを隔離する。既存セーブの移行方式は未決定。端末が主張するpaid残高や購入権を本番の実購入へ変換しない。

P0の設計指摘は文書へ反映済みだが、実装・実機・決済検証は未完了。詳細は [課金RV記録](reviews/monetization-review-2026-10-08.md)。
