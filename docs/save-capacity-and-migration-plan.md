# 保存容量の実機診断と将来のストレージ移行計画

更新日：2026-10-15

## 今回の実装

- 設定 → **端末のセーブ容量 → 保存状況を確認** を追加。Safari/PWA/iPhoneの画面から、自分の端末に**実際に保存されているJSON**の文字数・UTF-8容量、現在の未装備アイテム数、クラウド送信可否の事前判定を表示する。
- `navigator.storage.estimate()` と `navigator.storage.persisted()` が使える環境では、オリジン全体の推定使用量/上限・永続化状況を補助表示。IndexedDB APIが存在するかも確認。
- **すべて読み取り専用**。上限まで保存を試す破壊的なストレステスト、localStorageの上書き、IndexedDB/SQLiteへの自動移行、個別セーブデータの画面表示はしない。
- UIでもクラウド送信側でも `QPCore.saveDiagnostics` を使用し、**900 KiB（921,600）の安全な目安を文字数とUTF-8バイトの両方に適用**。従来の文字数制限以内でも、日本語のUTF-8によってFirestoreの1MiB近くへ達する送信を止める。実際のFirestoreドキュメントはメタデータ分も必要であり、この判定でも成功を保証しない。
- 現行のメインセーブ `jobquest_save_v1`、`schemaVersion`、`qp:saved`イベントとクラウド復元、オフライン精算は変更しない。PreviewとProductionの保存キー分離も維持。

## iPhone実機での確認手順

1. ソードクレストを開き、**設定 → 保存状況を確認**を押す。
2. 「端末の保存済みセーブ」と「現在の未装備アイテム」を確認する。セーブ後に再度押すと、最新の保存済みサイズを測定できる。
3. 「クラウド保存」が**送信文字数・UTF-8容量の基準内**か確認する。ただし通信・認証・Firebase Rules等は別問題なので、「今すぐバックアップ」の成功と最終バックアップ時刻も確認する。
4. 「ブラウザの保存領域」は**同じオリジン全体の概算**であり、localStorageだけの容量上限や実際の空き容量を保証しない。Safariが数値を返さない場合は「取得不可」で正常。
5. ホーム画面追加のPWAとSafariタブは認証状態・保存領域が異なることがある。どちらも使用する場合は**それぞれの環境で確認**する。プロトタイプと本番ドメインのデータは統合されない。
6. 保存失敗警告が出たときは、新しいデータが端末に書かれていない可能性がある。アプリを閉じる前に保存状況・バックアップ状態を確認し、必要なら不要装備を安全に整理する。**大量データや課金状態を無断削除して解決しない**。

## 保存方式拡張の設計（今回は未切替）

**重要：現行は同期APIのlocalStorage単一JSONが進行の正本。** `js/core/storage.js` の `getString`/`set`/`remove` は同期式。IndexedDBは非同期、iOSネイティブSQLiteは別の起動・書き込み管理が必要。名前だけ置換すると、起動処理・セーブ失敗処理・オフライン精算の安全性が壊れる。

### 推奨する段階的な工程

1. **診断（今回）**：端末で読み取ったJSONのサイズとクラウド制限を表示。移行可能性チェックは純粋関数 `migrationReadiness` で返し、移行操作はしない。
2. **別領域への複製（試作済み・実機未確認）**：WebではIndexedDB、iOSではSQLite等に、既存保存と別名のスナップショットを保存。書込み後に読み戻し、スキーマ版・長さ・ハッシュ・所持品/ロスター件数を照合。失敗時は元のlocalStorageを**一切削除しない**。
3. **移行リハーサル**：初回起動、クラウド復元、旧バージョンへの切り戻し、アプリ強制終了、容量不足、オフライン複数周回中の復帰、複数タブ/端末競合を試す。新旧二重書きの順番・整合性規則を決める。
4. **段階切替**：旧データを検証済みバックアップとして残し、新しい非同期保存層を**検証済みチェックポイント**として起動する。切り替え途中に保存失敗したら旧チェックポイントへロールバックできることを確認。完了前に元キーを削除しない。
5. **クラウドの大容量化**：Firestore単一ドキュメントへの全文JSON格納をやめ、変更を持つManifest（ユーザーID・スキーマ・世代番号・整合ハッシュ・保存時刻）＋アクセス制御されたBlob/Cloud Storageへ分離する候補を検討。Firebase認証・権限ルール・整合チェック・更新競合・Cloud Storage費用を別に設計。古い単一ドキュメントも復元可能な期間を設ける。
6. **課金権利を分離**：買い切り、購入履歴、有償残高、アイテム付与はバックアップのJSONや端末復元で増減させず、サーバーの課金台帳を正本とする。

### 完了判定（将来の段階切替PR）

- 旧セーブを移行・復元しても高品質OP、ロック、強化値、天井、ゲーム進行、自動周回の状態が変わらない。
- コピー書き込み・照合に失敗したら旧データがそのまま読み込める。**データが存在するのに空の初期セーブで上書きしない**。
- オフライン精算が、セーブの確定点をまたいで重複付与・報酬消失しない。
- サーバー台帳の課金権利とセーブの進行データを混同しない。
- 実機iPhone Safari/PWAでバックグラウンド終了・通信断・容量不足からの復帰が成功する。

`tests/save-capacity-diagnostics.test.js` に、クラウドの文字数と日本語UTF-8バイト、API拒否、設定画面のボタン、セーブ非改変、データ漏えい防止、スクリプト順序を追加。

## 2026-10-15：検証用IndexedDBコピーを追加（正式切替前の試作）

- 設定 → **IndexedDBへ検証コピー** は明示操作時のみ。従来のlocalStorageを読み出し、schemaVersion・仲間数・未装備品数・保存時刻・JSON文字数・UTF-8容量・SHA-256を検証する。
- Preview/Production/DebugでDB名を分離。IndexedDB内はa/bの2スロット方式。非アクティブ領域へコピー→読み戻し→JSON完全一致とSHA-256、件数等を照合→active管理ポインタ更新。コピーが失敗しても前回検証済みスロットを残す。
- コピー先は**起動時の復元に使わず**、ゲーム本体の同期保存・jobquest_save_v1・クラウド復元・オフライン精算・課金権利を変更しない。自動二重書きも行わない。
- **本物のバックアップではない。** 同じSafari/PWAオリジン上に置くため、ストレージ削除・端末故障・ブラウザデータ消去では両方消える場合がある。大容量のコピーには追加の空き容量が必要で、古い検証コピーを2スロット保持するためiPhoneの空き容量を圧迫する。容量不足時は新コピーを確定せず警告を表示する。
- tests/save-shadow-mirror.test.js で10,000件のコピー、2世代切替、読み戻し不一致、容量超過、無効JSON、環境分離を検証。**実WebKitトランザクション挙動はiPhone実機で別途確認が必要**。
- 次の工程：実機Safari/PWAでコピーが成功するか、バックグラウンド中断・ストレージ消去・数万件の容量不足を確認し、その後はクラウドの大容量化と整合ルールを設計。検証完了前にlocalStorageを正本から外さない。
